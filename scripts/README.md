# scripts

The portable, zero-runtime-framework Node tooling: the conformance gate, the tier report, the evaluator, and the check, generator, and shared-library modules they run on.

## Inventory

- `action-pin-watch.mjs` - the action-pin watch (E45, ADR 0053): resolves every `uses:` pin across the workflows and `action.yml` against the GitHub registry and reports where a pin s human-readable LABEL disagrees with what its machine-readable REF resolves to. Write-incapable. Exits 1 on a label problem and 2 when a lookup could not be performed; a pin merely BEHIND its action s current release is reported and exits 0, because that is somebody else s release cadence rather than a defect here. **Needs a token locally** - `GITHUB_TOKEN="$(gh auth token)" node scripts/action-pin-watch.mjs .` - or it meets GitHub s 60-per-hour unauthenticated limit and refuses.
- `audit-deps.mjs` - the dependency-audit gate (#310): runs `npm audit --json`, classifies the result through `lib/audit-report.mjs`, and exits 0 clean, 1 on a real advisory at or above the threshold, and 2 when the audit could not be PERFORMED. Write-incapable. `--report <file>` classifies a captured report with no network, which is how the outage is reproducible offline. It exists because `ci.yml` ran a bare `npm audit --audit-level=high` as the FIRST step of `validate`, and during the 2026-09-03 npm incident that step failed three times - skipping the unit tests, the coverage report and the conformance gate outright, while `validate` is a required check on `main`. So a required check went red on a run that never graded this repository at all, for a fact about somebody else's uptime. Two changes fix it: the audit now runs LAST, after everything it used to skip, and its verdict makes the same exit-code split `vendor-watch` and `action-pin-watch` already make (ADR 0053). Its regression corpus is `tests/fixtures/audit-deps/`, three outage shapes captured verbatim off the two runs that reded `main` plus a local run against a dead registry, so the guard is shown refusing and shown blocking rather than only shown passing.
- `check-claim-citations.mjs` - the claim-id reference guard (2026-08-28 audit row 7, spec RS-B4; it has no backlog entry, and an earlier draft of this line cited a non-existent "E57", which the guard itself could not catch because `scripts/` is outside its governed globs): every backticked kebab-case token that appears near the words "claim" or "pin", in `foundation/**` and the backlog, must resolve to a claim id in `foundation/claims/vendor-claims.json`. Report-only over documents; exits 1 on a citation that names no claim. It exists because four tracked surfaces asserted a pinned claim id that `git log -S` shows has never existed in the ledger at any commit, and nothing noticed for six days. The scoop subtracts the vocabularies this repository can enumerate from its own tree (source ids, skill directories, script basenames) plus a short committed list of names that are none of those, each entry saying what it actually is - an earlier draft that scooped by the words immediately preceding the id was measured against the four real lines and caught ONE. Its regression corpus is `tests/fixtures/claim-citations/pre-fix/`, the four offending lines captured verbatim, and the test asserts all four are named.
- `check-doc-enumerations.mjs` - the spine-enumeration guard: expands every reqId range written in the public docs (both the hyphen form and the word form, which spells the span with "through" or "to") and compares it against `scripts/lib/registry.mjs`, the one place the spine is real. Report-only over the docs; exits 1 on a stale claim. It exists because v1.15.0 fixed one stale page without sweeping or guarding, and by v1.16.0 the same staleness was live in eight more public files - `README.md` among them, where the correct list and a stale one sat six lines apart. History is exempt: `CHANGELOG.md`, `RELEASE-NOTES.md` and blockquoted version notes correctly state the numbers of their own day.
- `check-parity.mjs` - the first-party validator parity harness (ADR 0042): runs `claude plugin validate` and the skills-ref reference validator, round-trips every skill's `metadata.*` through the reference PARSER (not just the validator's exit code), and reports both validator identities and any pin skew. Report-only in this release; never gates.
- `check-readme-version.mjs` - front-door claim drift guard; asserts the README version badge, the `## Status` version / tier / skill-count / spine-size claims, every present-tense spine-size claim across the docs, and any self-referencing `@vX.Y.Z` tag advertised in action.yml / action.yaml all agree with library.json and the check registry.
- `check-release-notes-section.mjs` - the RELEASE-NOTES section gate and extractor (E57): asserts `RELEASE-NOTES.md` carries a `## <version>` section for the version in `library.json`, and with `--extract <version> --out <file>` writes that section out for `release.yml` to use as the GitHub release body. Both callers share `lib/release-notes-section.mjs`; neither reimplements the match. It exists because `release.yml` already refused to publish without that section and was RIGHT to, but ran the refusal in inline awk on the PUSHED TAG - so v1.17.1 was tagged, approved and served from npm with a literal unexpanded printf placeholder for a heading before anything objected. Being in YAML, that awk was also unreachable from `release-ready`, which is the gate that runs before the tag. Its regression corpus is `tests/fixtures/release-notes-section/`, the tagged tree captured verbatim at `754bb68~1` plus the same tree with only the heading repaired, so the gate is shown both refusing and passing.
- `check-release-counts.mjs` - release-time stated-test-count drift guard (backlog E27); runs the suite itself and fails on any hand-written test count that disagrees with the TAP-reported total. **Once a version is TAGGED, its release-plan packet and its CHANGELOG section stop being policed** (E52): both are records of what was true at that release, and policing them meant every test a later branch added forced an edit to a shipped document. `docs/internal/STATUS.md` is never exempt, because it is live state. The tag lookup **fails closed**, so a shallow clone with no tags polices everything exactly as before, and each exemption is printed in the OK line rather than applied silently.
- `check-self-consistency.mjs` - the generated-manifest guard: re-derives `manifest.generated.json` from `library.json` plus component frontmatter with the shipped generator and requires the committed file to equal it, reporting the four spine fields (`name`, `version`, `tier`, `standard`) against `library.json` directly before the first line where the two documents diverge. Report-only; exits 1 on drift and on an absent manifest, since the file is tracked. `check-self-consistency` runs in `npm test`, so this sentence is itself graded by `check-stale-state`. It exists because that file was the one generated artifact in the tree nothing compared against its source: measured on `main` at `3ee7170` on 2026-09-19, setting its `version` to 9.9.9 and its `standard` to 0.01 against a `library.json` reading 1.19.0 and 0.16 left `node scripts/check.mjs .` at 0 errors and 0 warnings AND the whole suite at 1659 tests with 0 failures. It was the only generated artifact in this tree with no guard at all, and the others were measured rather than assumed: hand-editing INDEX.md's first heading moves the gate from Advanced 0 errors to Convergent 1 error naming `index-drift` (`G4`); `U8` (manifest-drift) covers the two NATIVE manifests, on `name` and `version` only, and never reads this file; `gen-standard-coverage` without `--write` is the coverage page's drift mode. AGENTS.md is NOT on that list - `sync-agents-md` emits a `<!-- generated:components -->` block and this repository's AGENTS.md contains zero occurrences of that marker, so nothing is generated into it. **Component versions are deliberately NOT checked here** - `tests/unit/component-version-mirror.test.mjs` already compares every registered component's declared version against its own frontmatter and runs in `npm test`, measured on 2026-09-19 to fail on a drifted skill and on a drifted skill, subagent and command together. Line endings are normalized before comparing, because this tree is CRLF and the generator emits LF; a byte comparison would red on every Windows checkout. Its regression corpus is `tests/fixtures/self-consistency/`, three trees - the measured drift, the same tree repaired, and a body-only drift whose four spine fields are all correct, which is what proves the whole-document comparison is load-bearing rather than riding on the spine comparison.
- `check-stale-state.mjs` - the wiring-claim guard: every sentence in the governed live-state and public docs that binds a list of backticked script names to `npm test` (or `npm run <name>`) with a positive wiring verb must name scripts that package.json's resolved command chain actually invokes. Report-only over documents; exits 1 on a false claim. It exists because `docs/internal/backlog/enhancements.md` argued that `action-pin-watch` is uniquely exposed as a release-time gate and then listed `check-release-counts` among the guards that "runs in `npm test` and therefore on every pull request" - which was never true at any commit. Keeping that script out of the unit suite is a decision, not an impossibility: backlog E27 (the release-time stated-test-count gate) records it as wired to the release gate and deliberately not to `npm test`. The entry understated its own hole by half while reading as a careful measurement, and no existing guard could see it: `check-release-counts` polices a stale number, `check-doc-enumerations` a stale spine count, and this is a stale statement about the repository's own wiring. The scoop takes EVERY name in the claim's subject list rather than the one next to the verb - not because that is what caught this defect (the false name sat LAST of the four, so an adjacency rule would have caught it too) but so that a false name written earlier in a list is graded as well. A NEGATED claim is skipped, because "`X` does not run in `npm test`" is the shape the repair is written in. A path-existence design was built and measured first and rejected on evidence - see the `scoop-design` block in the file, which records the sweep counts and the reason it could not have fired on its own motivating defect. Its regression corpus is `tests/fixtures/stale-state/pre-fix/`, the offending line captured verbatim at `fabb38a` beside the repaired sentence, so the guard is shown both reding and staying green.
- `check.mjs` - the conformance gate entry point (runs every check, reports the tier and burndown; `--json`/`--sarif`/`--gha` emit machine-readable serializations of the same result).
- `checks/` - the per-requirement check modules.
- `doc-style-report.mjs` - the documentation style report: measures every published page against the per-quadrant page anatomy and the measurable floor in [`skills/askit-build-docs/references/style-contract.md`](../skills/askit-build-docs/references/style-contract.md), and ranks where prose work is worth doing. **Report-only and deliberately not wired into the gate**; it exits 0 unless asked for `--fail-on-breach`. It exists because "make it clearer" is an adjective that does not survive a handoff between sessions, while stacked sentences, overlong paragraphs and buried parentheticals are countable. Every signal it carries has a real false-positive surface: three separator forms had to be exempted before the counts meant anything, and an earlier draft rule contradicted a ratified decision about glossary links, so this reports for a human to read rather than blocking a release on a judgment-adjacent signal. Run it as `npm run doc-style`.
- `eval-run.mjs` - the eval-run pipeline CLI (grade a pinned corpus target, then aggregate the day's runs into the tracked record).
- `evaluate.mjs` - the structured evaluator behind askit-evaluate.
- `gen-family-registry.mjs` - the deploy-time family-registry generator (RS-D3): fetches the catalogue, checks every member out at the sha the catalogue PINS, grades the collection with the shipped `evaluate.mjs`, and writes the dated page the site serves. Generated rather than committed so its measurement date IS the deploy date - the hand-run snapshot it replaces went twenty days stale carrying a toolkit six releases old and three rows graded against drifted checkouts nobody could reproduce. **It never fails the site build:** an unreachable catalogue writes a dated could-not-measure page, an unreachable member degrades one row (the marketplace scope already reports an absent member as not-graded rather than red), and only being unable to write any page at all exits 1. It writes the MEASUREMENT and links the MEANING: `docs/reference/family-registry.md` keeps what the columns mean, why the collection reads as it does, and the record of the episode where an earlier version carried a false verdict - none of which is derivable from a run, and all of which a generator that overwrote the page would delete on its first deploy.
- `gen-site-reports.mjs` - the deploy-time report publisher (RS-D3): writes `tier-report.json`, the rendered HTML report and an index page into the Pages artifact, beside the badge and from the same sha, so the two cannot disagree about what was graded. It SPAWNS `tier-report.mjs --json` and `evaluate.mjs --format html` rather than reimplementing them - those are the commands the docs tell a consumer to run, and publishing a verdict computed by a path nobody else exercises would defeat the point. A non-zero exit from either is NOT an error here: they exit non-zero to report a failing grade, and a failing grade is the one a reader most needs to see; only empty output or a process that could not start is a failure. It also owns `TIER_SCOPE_SENTENCE`, the one canonical wording every surface presenting a tier inherits (RS-E3).
- `gen-tier-badge.mjs` - the CI-generated tier badge: serializes the tier `tier-report.mjs` already computes plus the graded sha, the plugin's pinned Standard, and a date into a shields.io endpoint-badge JSON document; run by `.github/workflows/deploy-pages.yml`.
- `gen-standard-coverage.mjs` - the Standard-to-check coverage generator and its drift guard (ADR 0059): extracts every RFC-2119 `MUST` clause from `STANDARD.md`, joins it against an authored disposition map validated against the live check registry, and renders `docs/reference/standard-coverage.md`. With no `--write` it fails when the page, the Standard and the registry have drifted apart. The `MUST` token count reconciles on every run - claimed clauses plus stated exclusions equal the raw count - because a clause the parser loses is one the table would silently declare covered, which is the failure ADR 0059 names as the risk of its own fix.
- `generators/` - the artifact generators (INDEX, manifests, AGENTS.md).
- `gha-action-outputs.mjs` - the outputs bridge behind `action.yml`; reads `check.mjs --json`, validates its shape (fails closed on a schema-incomplete report rather than defaulting), and prints the `tier`/`errors`/`warnings` GITHUB_OUTPUT lines the published Action exposes, so the Action's own YAML holds no validation logic.
- `gha-sarif-guard.mjs` - the SARIF artifact guard behind `action.yml` (v1.11.0 pre-release review, round 2): validates a completed `check.mjs --sarif` document's structural shape as its own signal, separate from exit-code agreement with the JSON gate, before `sarif-path` may be published; deletes the file on any rejection so a partial or disagreeing artifact never survives.
- `gha-step-summary.mjs` - the GitHub Action's job-summary writer (F-033): reads the same `check.mjs --json` report `gha-action-outputs.mjs` validates and APPENDS a Markdown job summary (tier plus counts, what blocks the next tier, the top findings grouped by reqId with a stated cap and an omission count) to `$GITHUB_STEP_SUMMARY`, never truncating it. Runs under `if: always()` in `action.yml`, so a failing gate still produces a summary; a missing `$GITHUB_STEP_SUMMARY` is reported to stderr and skipped, not a failure.
- `lib/` - the shared library used by the checks, generators, and gate.
- `release-ready.mjs` - the release-blocking gate aggregate (review wave 2, H2): runs the conformance gate, the README drift guard, the release-count guard, `vendor-watch`, `action-pin-watch` and the RELEASE-NOTES section gate, reports all six, and exits 1 if the tag must not be cut. Run by `release.yml` on the pushed tag and by `publish-npm.yml` on the candidate tree, so the checklist lines it replaced are enforced rather than remembered. **Run it locally as `GITHUB_TOKEN="$(gh auth token)" node scripts/release-ready.mjs`**; without a token the action-pin gate refuses on a rate limit, and the remedy is the token rather than `--allow-vendor-unreachable`.
- `standards-watch.mjs` - the upstream standards-watch CLI (compare the agentskills.io pin against what is current; prints, never writes).
- `tier-report.mjs` - the tier report (the satisfied tier plus the keyed burndown to the next).
- `vendor-watch.mjs` - re-verifies every VENDOR CLAIM this repository asserts as fact against the live page; write-incapable, exits 1 when a claim is gone or stale and 2 when a page could not be read.
- `verify-published-version.mjs` - post-publish registry assertion: after `npm publish` claims to have shipped, asks the npm registry itself whether the version the TAG names is actually there, and fails the run when it is not. Every other release control certifies what is about to ship; this is the only one that looks at the result, and it asks the registry rather than reading the local manifest the publish was derived from. Exits 0 when the registry serves the version, 1 when it answers and does not have it, 2 when it could not be read at all; a red here means UNVERIFIED, since nothing in it can undo a publish. Run by `.github/workflows/publish-npm.yml` as the last step of the `publish` job.
- `verify-release-tag.mjs` - release-tag format guard (v1.11.0 pre-release review, Finding 1): rejects any `workflow_dispatch` tag input that is not exactly `vX.Y.Z`, including shell-metacharacter injection payloads. Run by `.github/workflows/publish-npm.yml` from a `trust-root/` checkout of protected `main` - never the candidate tag's own tree - before the tag is used anywhere else (round 2 fix: the candidate must not supply the code that checks it).
- `verify-tag-ancestry.mjs` - tag-reachability guard (v1.11.0 pre-release review, Finding 2): fails closed unless a commit is a proven ancestor of `origin/main` via `git merge-base --is-ancestor`. Run by `.github/workflows/publish-npm.yml` from the same `trust-root/` checkout, against the tag's resolved sha, before the candidate is checked out at all and before any live npm publish (round 2 fix: this is the trust root's own code proving the candidate, not the candidate proving itself).
- `verify-tag-matches-manifests.mjs` - tag/version-manifest agreement guard: the four-manifest version comparison pulled out of the inline `run:` blocks in `.github/workflows/publish-npm.yml` and `.github/workflows/release.yml` and into a portable script (Standard sec 4.4); collects every disagreement rather than stopping at the first. Both workflows now call this one implementation, so a pre-publish guard cannot drift away from the GitHub-release guard. Takes `root` as a parameter, so `.github/workflows/publish-npm.yml` runs main's own copy (from `trust-root/`) with `root` pointed at the candidate's checked-out files - reading them as data rather than executing the candidate's own copy of this script.
