# 0035 - Manifest-vs-disk skill-registration completeness as a new Universal spine check (U13)

## TL;DR
- **Decision:** Add a new Universal/Bronze conformance check, `U13` `skill-registration`, that fails a plugin when a skill directory exists on disk (a `skills/<name>/SKILL.md`) but is not registered in the plugin's enumerating manifest (`library.json.components.skills[]`, or a `.claude-plugin/marketplace.json` `plugins[].source` pointing into `skills/`). It is an **objective** check (a set comparison between a registration list and a directory listing, zero judgment) and therefore survives `--profile plain-plugin`. Spine **29 -> 30**; Standard **0.11 -> 0.12** (the first growth since `U10` retired in v1.2.0). Per the burndown policy this Standard's own sec 7.7 commits to (ADR 0027), `U13` ships as a **`warn` for Standard 0.12** and graduates to a gate-failing **`error` at Standard 0.13** - making it the first live exercise of the burndown machinery v1.3.0 built but never ran. It is **distinct from `U8` `manifest-drift`** (which compares the generated native manifests against `library.json`); pick the non-colliding id `skill-registration`.
- **Plain language (why it matters):** a plugin that lists fewer skills in its catalog than it actually ships is silently delivering invisible skills - a user who installs it never sees the ones that were left out of the list. The real example that prompted this: `deanpeters/Product-Manager-Skills` ships 49 skills on disk but registers only 47 in its marketplace catalog, so two skills are invisible to anyone installing through the marketplace. This check catches that class of silent delivery failure for any plugin, on any agent, with no opinion about quality - just "did you list everything you shipped."
- **Why a spine check (not a side-channel validator):** "every skill you ship is registered" is a property of the **plugin itself** and is fully objective and portable, which is exactly the Universal/Bronze tier's definition. Routing an objective, portable, plugin-intrinsic defect to a non-spine validator would let a plugin shipping invisible skills still be graded **Gold**, eroding what the grade means. The timing is also right: no third party is known to grade against the Standard yet, so this is the lowest-risk moment to demonstrate the Standard can grow responsibly, and ADR 0027's pinned-version downgrade plus the warn-first burndown cushion the churn twice over.
- **Status:** Accepted (ratified in the v1.6.0 release that ships U13, mirroring how ADR 0027 was ratified by the release that implemented it, and ADR 0028 by v1.2.0).

- **Status:** Accepted
- **Date:** 2026-06-13 (ratified 2026-06-14, v1.6.0)
- **Deciders:** maintainer (jprisant), with Claude (Opus 4.8)

## Builds on
- **ADR 0027 (Standard versioning and compatibility policy)** - provides the two mechanisms that make a spine addition safe: (a) the **warn-for-one-minor burndown** (STANDARD.md sec 7.7), which requires a new MINOR requirement to ship as `warn` first, so `U13` cannot gate-fail anyone in 0.12; and (b) the **pinned-version downgrade** (`applyStandardDowngrade`), which, once `U13` becomes an `error` at 0.13, surfaces it as a `warn` for any plugin still pinning 0.12 or below. `U13` is the first requirement to exercise the burndown that v1.3.0's F1 built but left dormant ("no live burndown in this PR").
- **ADR 0028 (retire U10 from the spine)** - sets the legitimacy bar a check must clear to earn a spine slot: it must proxy a real outcome the consumer cares about, grounded in objective correctness or cited external authority, not house taste. `U10` was retired for being taste with no portability basis. `U13` is the opposite case: pure objective correctness (a skill that is on disk but unregistered is genuinely undeliverable through the catalog), no judgment, no vendor-specificity. ADR 0028 also confirmed that a Standard version change is routine when justified.
- **plan_v1.3.0 PROGRAM-PLAN sec 7.2 (the `config-valid` spine decision)** - the precedent that a candidate check is kept *off* the spine when it "is not part of the plugin conformance contract" and "is vacuous for the common no-config plugin." `U13` is the inverse: it is squarely part of the plugin conformance contract (a property of the plugin's own catalog) and is non-vacuous for any plugin with skills. So this ADR applies the sec 7.2 test, it does not overturn it; the `U13` slot the `config-valid` SPEC hypothesized was never consumed (config-valid shipped as a `reqId:null` validator), so the number is free.
- **Eval-run sensor reading 12** (`docs/internal/eval-runs/eval-runs.md`) - the observation that manifest-vs-disk skill drift is an objective new-check candidate, recorded during corpus batch 2 (2026-06-10) against the deanpeters target, flagged as needing an ADR before building.

## Context and problem statement
The toolkit grades whole libraries against a deterministic tier ladder. Its outward-grading runs (the eval-run program) surfaced a portable defect the spine does not catch today: a plugin can ship a skill on disk without registering it in the catalog that installers read, so the skill is delivered but invisible. The concrete case, reading 12: `deanpeters/Product-Manager-Skills` (pinned clone at `E:/tmp/eval-deanpeters-pm` @ `70fb6c4`) has 49 skill directories under `skills/`, each a valid `SKILL.md`, but its `.claude-plugin/marketplace.json` `plugins[]` array registers only 47 (its own `metadata.description` says "47 battle-tested ... skills"). Two skills are shipped but catalogued nowhere; a user browsing or installing through the marketplace never sees them.

The registration surface is plugin-shape-dependent, which the check must handle:
- A `library.json`-based library (the askit shape) enumerates skills in `components.skills[]` (each `{name, path}`). This is the authoritative registration list.
- A Claude marketplace-of-skills (the deanpeters shape) registers each skill as a `plugins[]` entry in `.claude-plugin/marketplace.json`, with `source: "./skills/<name>"`.
- A bare `.claude-plugin/plugin.json` with no skill enumeration relies on Claude Code auto-discovering everything under `skills/`. Here the manifest enumerates nothing, so disk *is* the registration and no drift is possible. The check MUST NOT false-fire on this shape.

This is **not** the existing `U8` `manifest-drift` check. `U8` asserts that the committed *generated native manifests* (`.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`) match what `gen-manifest` produces from `library.json` - an internal generator-consistency invariant tied to the release tag guard. `U13` asserts that the *human-authored registration list* enumerates every skill that physically exists. Same word "drift," orthogonal defect, different inputs. The shared "manifest" vocabulary is why the new check takes the distinct id `skill-registration` rather than any `manifest-*` name.

## Decision drivers
- **Objectivity.** The check is a set comparison between a registration list and a directory listing. There is no model, no judgment, no taste. It is the strongest provenance class (`objective`), the one ADR 0029 reserved for portable, vendor-neutral correctness.
- **Portability.** "Register what you ship" is true for any plugin, any agent, regardless of house style. It is not an askit convention; it is a property of a well-formed catalog. So it belongs in the portable floor and survives `--profile plain-plugin`.
- **Non-vacuity.** Unlike the `config-valid` candidate that plan_v1.3.0 kept off the spine (vacuous for the common no-config plugin), `U13` evaluates real on-disk skills against a real manifest for any normal plugin. It only passes trivially for a zero-skill plugin, an edge that is correctly "nothing to drift."
- **Tier-ladder integrity.** The grade must mean something. A plugin that silently drops skills from its catalog is not well-formed; allowing it to still reach Gold (which a non-spine validator would) quietly weakens every grade. A Universal check keeps "you cannot be Gold while shipping invisible skills" true.
- **Timing and reversibility.** No external party is known to grade against the Standard yet (the standing post-1.1.0 task is "ratify ADR 0027 before any third party grades against it"). Growing the Standard now, before external lock-in, is the lowest-risk moment. Freezing later is easy; un-freezing an ossified Standard is hard.
- **The churn is doubly cushioned.** The burndown (warn in 0.12) means no plugin hard-fails on `U13` in v1.6.0; the pinned-version downgrade means a 0.12-pinned plugin still sees only a warn after `U13` graduates to error at 0.13. The cost is a documentation sweep, not a downstream break.

## Considered options
1. **A new Universal spine check `U13` `skill-registration` (chosen).** Objective + portable + plugin-intrinsic + non-vacuous is the Universal-tier definition; the burndown and pinned-downgrade make the growth safe; the tier ladder stays honest. Cost: the full Standard sweep (STANDARD.md spine line and a new normative subsection, the count asserted across tier-report / explanation tables / README / tests, the Standard 0.11 -> 0.12 bump) and the burndown discipline (ship warn, graduate later).
2. **A non-spine objective validator (`reqId: null`).** Ships the same comparison as a finding in `check.mjs` / `evaluate.mjs` with no Standard change and no contract churn. Rejected as the home (kept only as the fallback if the maintainer prefers a frozen Standard): it under-claims a genuinely portable requirement, cannot gate a tier (so a plugin shipping invisible skills could still be graded Gold), and sets a precedent that the Standard is frozen and new objective requirements go to a side channel, which ossifies the Standard exactly when it should be demonstrating responsible growth.
3. **A Silver or Gold check rather than Universal.** Rejected: manifest completeness is fundamental well-formedness, not a convergent or advanced refinement. A plugin that does not register what it ships fails the most basic catalog contract; putting it above Bronze would say a Bronze plugin may ship invisible skills, which is wrong.
4. **Do not build it; document the limitation.** Rejected: reading 12 is a real, reproduced, portable defect with a named real-world instance. Leaving the gate blind to silent delivery failures undercuts the toolkit's outward-grading legitimacy.

## Decision outcome
Option 1. The new check ships as `scripts/checks/skill-registration.mjs` with `meta = { id: "skill-registration", tier: "universal", reqId: "U13", since: "0.12", provenance: "objective" }`, registered in `scripts/lib/registry.mjs` after `U12`.

**What it checks (the canonical buildable scope lives in the F1 SPEC/IMPL; the contract here):**
- **Resolve the registration source by precedence:** (a) `library.json.components.skills[]` if a parseable `library.json` with a skills array is present; else (b) `.claude-plugin/marketplace.json` `plugins[]` entries whose `source` resolves under `skills/`; else (c) **no enumerating manifest -> the check passes** (auto-discovery shape; nothing to drift, no false positive).
- **The on-disk set** is the skill directories the loader already enumerates (`ctx.skills`, a `skills/<name>/SKILL.md` per the existing `listSkillDirs`/`loadSkill`).
- **The headline defect (error class at 0.13):** a skill on disk that is absent from the registration source (the deanpeters 47-of-49 case) - "shipped but unregistered / invisible."
- **The reverse defect (phantom registration):** a registration entry whose skill directory does not exist on disk - "registered but undeliverable." The SPEC carries both directions as the fuller integrity vision; the IMPL-PLAN may scope v1.6.0 to the headline under-registration case and record phantom-registration as a fast-follow if the bidirectional comparison is not free. (It is free for `library.json`, where the path is checkable, so the default is bidirectional.)

**Severity and the burndown (the dogfood):** because introducing a new Universal requirement at MINOR 0.12 triggers STANDARD.md sec 7.7's warn-for-one-minor rule, the `skill-registration` module **emits `SEVERITY.WARN` in v1.6.0 / Standard 0.12**. It is surfaced on every plugin (the deanpeters case shows as a `[warn]`), gates nobody, and is the first real customer of the burndown. A later release at Standard 0.13 flips the module's emitted severity to `SEVERITY.ERROR` (the per-check flip mechanism v1.3.0 chose over an `enforcedSince` field; there is no `enforcedSince` in the shipped gate). From 0.13 on, `applyStandardDowngrade` surfaces it as a `warn` for any plugin pinning 0.12 or below, so the courtesy window is preserved per-consumer too.

**Dogfood invariant:** the toolkit registers all 23 of its on-disk skills in `library.json.components.skills[]` (verified: 23 registered, 23 directories), so `U13` is clean for the toolkit - not even a warn - and `node scripts/check.mjs .` stays Advanced 0/0. The Standard 0.12 bump does not change the toolkit's own grade.

**The sweep (v1.6.0):** `STANDARD.md` gains the `U13` requirement text and moves its spine line to 30 checks and its version to 0.12; `library.json.standard` -> `0.12`; the 29-count assertions across `registry-sync`, the explanation tables (`docs/explanation/conformance-and-tiers.md`), the new `docs/reference/universal-checks.md` page (F4), `README.md`, `AGENTS.md`, and `MEMORY` move to 30; the F4 per-check glossary picks up the new check's `why:` docblock line automatically.

## Consequences
- **Positive:** the gate catches a real, portable, silent delivery failure (invisible skills) for any plugin; the Standard demonstrates that it can grow responsibly, with the burndown and pinned-downgrade proving the v1.3.0 compatibility machinery in production; the tier ladder stays honest (no Gold while shipping invisible skills); the `objective` provenance keeps it valid under `plain-plugin`, so it strengthens outward grading rather than adding house noise.
- **Negative:** the first Standard MINOR bump since 0.11 carries a documentation sweep and a count change across many surfaces (mitigated: the surfaces are enumerated above and guarded by `registry-sync` and the F4 route/count checks); the requirement is a `warn` for one full release line before it can gate, so the deanpeters-class defect is surfaced-but-not-blocked until 0.13 (accepted: this is the burndown contract working as designed, not a gap).
- **Neutral:** a third Standard-vs-disk concept now exists (`U8` generated-manifest-vs-`library.json`, `U13` registration-vs-disk, and the `S6`/`per-target-presence` native-presence check); the F1 SPEC and the new `docs/reference/universal-checks.md` page disambiguate them so a reader is not confused by the shared "manifest" word.
