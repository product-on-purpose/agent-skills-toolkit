# 0037 - The builder craft pass: an optional improve-mode phase 2 and the SAFE/JUDGMENT partition contract

## TL;DR
- **Decision:** `askit-build-skill` improve mode gains an **optional phase 2** that runs only after the deterministic gate is already clean. It dispatches the `askit-reviewer` subagent against a written rubric (`skills/askit-build-skill/references/skill-craft-rubric.md`, five dimensions: description and trigger quality, instruction clarity, example depth including golden and anti-example presence, reference structure, token economy), renders the findings through the existing `evaluate.mjs --report=review` advisory path as a durable Markdown or HTML artifact, and partitions them with a new pure module `scripts/lib/craft-review.mjs` into **SAFE** (a closed allowlist of three mechanical categories) versus **JUDGMENT** (everything else). Only the SAFE subset is ever offered for an automatic apply, and only with `consent: true`. Spine stays 30, Standard stays 0.12; no check is added or changed.
- **Why:** The builder can already say whether a skill obeys the rules. It cannot say whether the skill is any good as a teacher, and the deterministic checks structurally cannot: U5 (description-score) is a heuristic that scores "Use when the user asks about the document thing" at **1.00**, and U6 (reference-links) scans `SKILL.md` and `references/` only, so a dangling link in `examples/` is invisible to it. Both gaps are real, both are reachable by a reading reviewer, and neither is a check the gate should grow (a model in the gate would end its determinism). An advisory second opinion is the right shape for it.
- **The safety property that makes an auto-apply defensible:** SAFE is a **closed allowlist that fails toward "do not touch"**. An unknown category is JUDGMENT. A SAFE category with no bounded fix descriptor is JUDGMENT. A multi-line or over-length substitution is JUDGMENT, which is what stops an instruction rewrite from being laundered through the `formatting` category. A fix target that is absolute or escapes the skill directory is JUDGMENT. `description` and `name` are excluded from the frontmatter-field allowlist because they carry meaning. The applier **re-classifies every finding it is handed**, so a caller cannot smuggle a JUDGMENT finding past it.
- **Status:** Accepted.

- **Date:** 2026-07-26
- **Deciders:** maintainer (jprisant), with Claude (Opus 5)

## Builds on
- ADR 0027 (Standard versioning) - phase 2 changes no requirement, so there is no spine or Standard movement. The Standard stays 0.12 and the spine stays 30 checks.
- The v1.4.0 E1 report renderer and its `applyAdvisory()` allowlist merge (`scripts/evaluate.mjs`) - the pre-existing seam that makes an advisory layer structurally unable to move the verdict. Phase 2 reuses it rather than inventing a second advisory path.
- ADR 0033 (recalibrate U5 description scorer) - it made the deterministic scorer good, and in doing so drew the line this ADR builds on: a lexical heuristic can verify FORM (an action verb, a use-when clause) and can never verify whether a trigger names words a user would type. That residue is craft, and it needs a reader.
- ADR 0032 and ADR 0036 (U6 calibrations) - they narrowed U6 to LIVE content it can resolve. The complement is that link rot outside its scan set (`examples/`, prose in a sibling file) has no deterministic owner, which is one of the two defects the phase-2 fixture demonstrates.

The partition is the mechanical expression of that lesson: the tool acts only where verification is unnecessary because the edit is mechanical.
- `docs/internal/execution/04-releases/R1-v1.7.0-trust-and-craft.md` (bundle SP1, builder craft pass) - the release plan this implements, including its stated invariants.

## Context and problem statement
Improve mode today is a conformance loop: run the gate, fix what it flags, re-run. When the gate goes clean the loop ends, and everything the gate cannot see ends with it. Three concrete gaps, all reproducible in the fixture at `tests/fixtures/anti/craft-defects/summarize-doc`, which passes the gate with **0 errors and 0 warnings**:

- **A well-formed, useless trigger.** `description: Converts a document into a summary. Use when the user asks about the document thing.` scores **1.00** on U5: it has an action verb, a use-when clause, enough words, and no first-person voice. The trigger names nothing a user would ever type. The scorer is not broken; this is the ceiling of a lexical heuristic.
- **Link rot outside the deterministic scan set.** U6 resolves relative links in `SKILL.md` and `references/*.md`. A dangling link in `examples/basic.md` is not a U6 finding, and widening U6 to every file in a skill directory is a separate, riskier calibration with its own false-positive surface.
- **Nothing at all about teaching quality.** Whether examples are real, whether an anti-example exists, whether the procedure contradicts itself, whether the body is paying rent: no check covers any of it, and none should. These are judgments.

The maintainer's stalled 2026-06-25 design named the shape of the answer (an AI craft pass with consent-gated auto-fix). The open question this ADR had to settle is the dangerous one: **which findings, if any, may a tool apply on a user's behalf when the findings come from a model?**

## Decision drivers
- **The advisory layer must never move the gate verdict.** This is the toolkit's central trust claim (Design Principle 3, and the property the token dossier tells budget-conscious users they can rely on when they choose a cheaper model). A craft pass that could change a pass into a fail would break it.
- **Never edit without consent.** An improve loop that silently rewrites a user's skill is worse than no improve loop.
- **Fail closed, not open.** The findings are model-authored. The failure mode to design against is not "the tool missed a safe fix", it is "the tool confidently applied a wrong one". A missed SAFE fix costs one manual edit; a wrong applied edit costs trust.
- **The judgment findings are the point.** A sharper trigger is worth more than a fixed typo. The design must not make JUDGMENT feel like the reject pile: it is reported, in the durable artifact, with the recommended change.
- **Relocation separability.** Release 1 is the first release to add engine-adjacent code. The new module must sit cleanly on the evaluate/advisory side of the seam, not in the deterministic check spine.
- **No new check.** Whatever else phase 2 does, it does not grow the Standard. Craft is not conformance.

## Considered options
1. **An optional phase 2: rubric-guided reviewer, advisory render, closed-allowlist SAFE partition, consent-gated apply.** (chosen) Detailed below.
2. **Grow the spine with craft checks instead.** Rejected: the reachable part of craft is already checked (U5 form, U6 live links, U7 budget), and the unreachable part needs a reader. A check that needs a model is not a check; it would end the gate's determinism, its zero-token property, and its reproducibility in one move.
3. **Run the craft review as part of phase 1, on every improve run.** Rejected on two grounds. It would spend an advisory subagent run (measured 33k-103k tokens) on every improve invocation, including runs whose gate is red and whose craft findings are therefore premature; and it would blur the boundary the whole design rests on, since a user watching one combined pass cannot tell which findings are the gate's and which are a model's opinion.
4. **Apply every finding the reviewer marks fixable, trusting the reviewer's own judgment about safety.** Rejected outright. It inverts the fail direction: an unknown or novel category would be applied by default, which is the exact shape of the recorded confabulation failures (a Haiku-tier reviewer at high effort inventing a statute correction, sensor reading 17). Safety must be decided by a closed list the tool owns, not by a claim in the payload.
5. **A denylist instead of an allowlist (apply anything except an enumerated set of dangerous categories).** Rejected for the same reason, one step subtler: a denylist is only as complete as the imagination of whoever wrote it, and it silently admits every category invented after it was written. The allowlist's default answer to a novel category is "no", which is the correct default.
6. **Let the SAFE fix be a free-form patch or a diff the reviewer authors.** Rejected: an arbitrary patch cannot be bounded, so "mechanical" would become unverifiable. Requiring a **bounded, single-line literal substitution** (or one allowlisted frontmatter field) is what lets the applier prove, without reading semantics, that the edit cannot restructure prose. It costs real coverage: a legitimate multi-line formatting repair such as reflowing a table is JUDGMENT under this rule. Accepted deliberately, and stated in Consequences.
7. **Include `description` in the SAFE frontmatter-field allowlist**, since a missing description is a mechanical omission the Standard requires. Rejected: filling in a description means AUTHORING a description, which is dimension 1 of the rubric and the single field most responsible for whether the skill is ever loaded. A generated description that scores 1.00 and triggers on nothing would be the worst possible outcome of a tool meant to improve craft.
8. **Render the craft review to chat only.** Rejected: the findings are exactly the sort a maintainer wants to share, revisit, or attach to a PR, and a durable artifact is already free (the E1 renderer plus `--report=review`). Reusing that seam also means the craft review inherits the advisory labeling, the model and effort provenance stamp, and the escaping hardening from v1.4.1.
9. **A dedicated `--report=craft` type in the renderer.** Rejected as unnecessary surface: craft findings are advisory review findings with a rubric dimension in the `area` field. The disposition is carried in the message as a `[SAFE]` or `[JUDGMENT]` tag, so no renderer change ships with this ADR at all.

## Decision outcome
Option 1, in four parts.

**1. The rubric (`skills/askit-build-skill/references/skill-craft-rubric.md`).** Five dimensions, each with what to judge and the ceiling of the deterministic check that neighbours it. It also carries the finding contract, so the reviewer emits partitionable output: `dimension`, `category`, `severity`, `file` (relative to the skill directory), `message` (quoting the line judged), `provenance`, and `fix` for mechanical categories only. It instructs the reviewer to verify before asserting, to say "unverified" rather than invent a correction, and never to recommend a gate change from that seat.

**2. The partitioner (`scripts/lib/craft-review.mjs`).** A pure module, no gate imports, five exports:

- `SAFE_CATEGORIES` (frozen): exactly `broken-link`, `formatting`, `missing-frontmatter-field`.
- `SAFE_FRONTMATTER_FIELDS` (frozen): exactly `metadata.version`, `metadata.tier`, `metadata.audience`, `metadata.status`.
- `classifyCraftFinding(f)` returns `{ disposition, category, reason }`. Every rule fails toward JUDGMENT: a non-object finding; a missing or non-string category; a category not exactly on the allowlist after lexical normalization (trim plus lowercase, which cannot change WHICH token was named, so `broken link` with a space is a different category and is JUDGMENT); a `file` that is absolute, carries a drive letter, or contains a `..` segment; a `fix.kind` that is not the kind that category owns; a substitution that is empty, multi-line, over `MAX_SAFE_EDIT_CHARS` (200), or a no-op; a frontmatter field outside the field allowlist or with an empty value.
- `partitionCraftFindings(findings)` returns `{ safe, judgment, decisions }`, where `decisions` is one record per input in input order carrying the stated reason, so the report can say why each JUDGMENT finding was left alone. A non-array input yields two empty buckets rather than throwing.
- `phaseTwoEligible(gate)` gates the OFFER on a clean gate: eligible only when `exitCode === 0`, and not when a caller passes `exitCode: 0` alongside a non-zero error count (an inconsistent result is treated as not clean). An unknown gate result is not clean.
- `applySafeFixes(root, findings, { consent })` writes only when `consent === true` (not truthy: exactly `true`), re-classifies every finding and refuses any that is not SAFE, refuses a target that does not exist, and refuses a literal that is absent or occurs more than once rather than guessing which occurrence was meant. A frontmatter insert refuses when a key of that name already appears in the block, which also makes it idempotent. It normalizes path separators and re-asserts containment against the resolved subject root at the WRITE site (belt to the classifier's braces), and it inserts the replacement through a function replacer so a `$` pattern in a model-authored payload cannot splice in surrounding text. Every refusal is returned with a reason; nothing is dropped silently.
- `toReviewAdvisory(findings, meta)` shapes the set as the `--report=review` advisory block, tagging each message `[SAFE]` or `[JUDGMENT]` (a judgment finding also carries the reason it was not auto-applied) and adding one insight stating the partition counts.

**3. The procedure (`skills/askit-build-skill/SKILL.md`).** Eight steps: check eligibility, offer and stop, dispatch `askit-reviewer` with the rubric, render the durable artifact, partition, offer the SAFE subset item by item with before and after, report the JUDGMENT findings without acting, re-run the gate. The chain edit permits `askit-build-skill` to invoke `askit-reviewer` (`agents/_chain-permitted.yaml`), the frontmatter `chain:` declares it, and `evals/build-skill-to-reviewer.eval.json` covers the new edge (G3 requires an eval per chain edge, including the negative case that a red gate does not dispatch).

**4. No renderer change and no check change.** The advisory rides `applyAdvisory()` exactly as the v1.4.0 review report does.

**Tests (TDD, RED first).** `tests/unit/craft-review.test.mjs` (29; the first 26 opened RED against a deliberately fail-open placeholder, 25 of them failing, including "an unrecognized category is never SAFE"). Seeded with real-shaped findings: three known-SAFE (a broken link, a missing frontmatter field, a formatting defect), two known-JUDGMENT (an instruction rewrite, a procedure change), and one unknown category carrying a well-formed fix, which must still be JUDGMENT because a valid fix shape alone does not buy SAFE. Nine of the tests are fail-closed guards, one per laundering route. Three more came out of the adversarial self-review of the applier, each a real defect at the time it was written: the replacement is inserted through a function replacer (string-form `replace` would expand a `$&` in a model-authored payload and splice in surrounding text), a Windows-style relative path is normalized before the write site re-asserts containment, and an INLINE frontmatter map (`metadata: {version: 1}`) is refused rather than given a duplicate YAML key. `tests/integration/craft-review-flow.test.mjs` (2) runs the whole flow over the real CLI seams against the gate-clean, craft-defective fixture. Suite 442 -> 473; gate Advanced 0/0.

**The invariant proof.** Two tests exercise both directions with a hostile advisory that also carries `findings`, `summary`, `byRule`, and `tier` keys: a craft advisory cannot fail a subject the gate passes, and a clean craft advisory cannot pass a subject the gate fails. The mechanism is structural rather than defensive: the gate exit code is computed by `gateExitFromFindings()` from `report.findings`, and `applyAdvisory()` merges base-first and then only its own namespaced keys (`reportType`, `review`, `insights`), so no advisory field can reach `findings`, `summary`, `byRule`, or `tier`. The tests assert the resulting exit code, not the merge's internals.

## Consequences
- **Positive.** The improve loop finally has something to say after the gate goes clean, and it says it in a durable, shareable artifact that carries its own model and effort provenance. The two defects the fixture demonstrates (a 1.00-scoring vacuous trigger, link rot outside U6's scan set) are exactly the class the toolkit's own eval runs kept surfacing by hand. Phase 2 is opt-in and offered, so its token cost is never spent on a user who did not ask for it, and never on a run whose gate is red.
- **Deliberate coverage cost: the bounded-edit rule refuses legitimate mechanical fixes.** A multi-line formatting repair (reflowing a table, re-indenting a fenced block) and a substitution longer than 200 characters are JUDGMENT, even when a human would call them obviously safe. This is the price of being able to prove, without semantic reading, that a SAFE edit cannot restructure prose. The user still gets the finding and the recommended change; they apply it themselves.
- **Deliberate coverage cost: an ambiguous literal is refused.** If the text to replace occurs twice, the apply is skipped rather than applied to the first match. Correct for a mechanical applier, occasionally annoying for a real repeated typo.
- **The already-present frontmatter test is broad, and an inline map is refused.** The present-key test scans the whole frontmatter block for a key of that name, so a top-level `version:` blocks a `metadata.version` insert; and a parent map written inline (`metadata: {version: 1}`) is refused rather than edited, because appending a second `metadata:` key would write duplicate YAML. Both refuse in the fail-closed direction; stated so the breadth is a decision rather than an oversight.
- **Residual, stated rather than closed: symlinks.** Containment is enforced on the path text (no absolute path, no `..`) and re-asserted on the resolved path at the write site, but a symlink INSIDE the skill directory pointing outside it would still be followed by the write. The threat model here is a model writing a wrong path, not an adversarial repository the user is deliberately improving, so this is accepted rather than fixed. Recorded so a future adversarial-scope change knows where to look.
- **Craft-review quality varies with the model, and the floor is not verification.** Per sensor readings 14, 16, and 17, a Haiku-tier reviewer can assert false consistency and confabulate corrections at any effort. The partition contains the damage (a confabulated JUDGMENT finding is reported, not applied; a confabulated SAFE finding still has to name an allowlisted category AND a bounded literal that exists exactly once in a contained file), but it does not make a cheap review good. The dossier row recommends Sonnet 4.6 at medium as the default and a frontier model at high effort for a decision-critical pass.
- **A new chain edge means a new eval and a new permission.** `askit-build-skill` can now invoke `askit-reviewer`, which was previously reachable only under `askit-evaluate`. The edge is declared in the frontmatter, permitted in the contract, and covered by an eval, so S4 (chain-contract) and G3 (library-regression) both hold.
- **No conformance implication.** Spine stays 30 (U1-U9, U11-U13, S1-S8, G1-G10), Standard stays 0.12, no check gained or changed provenance, and the toolkit still self-grades Advanced 0/0. Nothing the Standard required before, it still requires.
- **Relocation.** `scripts/lib/craft-review.mjs` is recorded in `docs/internal/execution/relocation-addendum.md` as **retained** (evaluate-side): it imports nothing from the check spine, rides the `evaluate.mjs` advisory path, and stays with askit if the checker relocates.

## Implementation sites
- `scripts/lib/craft-review.mjs` - `SAFE_CATEGORIES`, `classifyCraftFinding()`, `partitionCraftFindings()`, `phaseTwoEligible()`, `applySafeFixes()`, `toReviewAdvisory()`: the entire partition contract; the SAFE allowlist is frozen here and re-asserted by the applier at the write site.
- `skills/askit-build-skill/SKILL.md` - phase-2 procedure (steps 1-8): the authored skill instructions that invoke `askit-reviewer` with the craft rubric and call `applySafeFixes` with `consent: true` for SAFE findings only; the skill is the user-visible surface of this decision.
- `skills/askit-build-skill/references/skill-craft-rubric.md`: the five-dimension rubric the `askit-reviewer` subagent reads; the finding schema (dimension, category, severity, file, message, fix) that `classifyCraftFinding` expects is specified here.
- `agents/_chain-permitted.yaml` - `askit-build-skill` entry: the chain contract that permits `askit-build-skill` to invoke `askit-reviewer`; without this entry S4 (chain-contract) would fire as an error.
- `evals/build-skill-to-reviewer.eval.json`: the G3 eval that covers the new chain edge (the positive case and the gate-red negative case that must not dispatch).

Grep anchor: `SAFE_CATEGORIES` in `craft-review.mjs` (the allowlist that defines the decision's safety property); `askit-reviewer` in `agents/_chain-permitted.yaml` (the chain permission).
