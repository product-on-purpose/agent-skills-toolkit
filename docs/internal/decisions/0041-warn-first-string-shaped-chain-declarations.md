# 0041 - String-shaped chain declarations are warn-first, not gate-tightening

## TL;DR
- **Decision:** `S4` (chain contracts, `scripts/checks/chain-contract.mjs`) reads a STRING-shaped `metadata.chain` (or legacy top-level `chain:`) declaration, but a finding that is reachable ONLY through that shape - an orphan, or "chaining is used but `agents/_chain-permitted.yaml` is missing" - is `SEVERITY.WARN` at Standard 0.12, not `error`. The identical finding reached through an ARRAY-shaped declaration, an existing contract file, or `_workflows/`, stays `error`, unchanged. The `warn` graduates to `error` at Standard 0.13.
- **Why:** main never parsed a string-valued `chain` at all - it silently produced an empty chain and could not gate. The v1.10.1 fix (ADR 0040) taught `S4` to read that shape, which is correct, but shipping it as an immediate `error` would let a Convergent plugin pinned to Standard 0.12 flip from passing to gate-failing solely by upgrading the toolkit, with zero change to itself. `S4` still declares `since: "0.x"`, so the existing pinned-version burndown machinery (ADR 0027) cannot downgrade this on its own; the severity has to be decided at the point each finding is built, by the shape that produced it.
- **Found by adversarial review, not by the author.** The release plan for v1.10.1 asserted "no third-party plugin's tier or exit code moves" as the release invariant; the implementation that shipped to review (PR #205, `8f31845`) carried a carve-out against exactly that invariant. See Context below for how it got through.
- **Status:** Accepted.

- **Date:** 2026-08-11
- **Deciders:** maintainer (jprisant), with Claude (Opus 5)

## Builds on
- ADR 0027 (Standard versioning and compatibility policy) - the warn-for-one-minor burndown this decision invokes, and the reason a per-check `since` alone cannot express it: `since` marks when a *check* was introduced, not when a *shape within an existing check* started being read.
- ADR 0040 (re-pin agentskills.io after an editorial metadata clarification) - the change this decision governs. ADR 0040 taught `S4` to read `metadata.chain` as a string, and stated: "That reader change is purely additive: no third-party plugin's `S4` verdict moves." That statement is corrected here: it was true only for the plugins that happened to have no unpermitted string-shaped edge; a plugin that did was newly gated. This ADR does not reopen ADR 0040's decision to read the string shape - it fixes the severity that decision shipped with.
- PR #204 (chain frontmatter migration) - moved `chain` under `metadata` to satisfy the agentskills.io vocabulary. That move is what exposed that `skills-ref` coerces every `metadata` value through Python's `str()`, silently turning a YAML list into a string containing a Python list repr - fixing that required a string form, and teaching `S4` to read the string form is the reader change this ADR governs the severity of.
- v1.10.0's `G4` (generated-docs drift) index-drift migration (RELEASE-NOTES.md "Upgrade" section, recorded in commit `3c9197a`) - the precedent this decision distinguishes itself from; see Decision outcome.

## Context and problem statement

`scripts/checks/chain-contract.mjs` resolves a component's declared invocation from `metadata.chain`, falling back to a legacy top-level `chain:` key. Before ADR 0040, `parseChainDeclaration` handled only the array shape; a string fell through to `[]`, so a string-valued `chain:` produced no declared invocation, could not appear in `declaredChains`, and could not flip `chainingInUse` or trigger an orphan. Main was therefore blind to a string-shaped `chain:`, silently.

ADR 0040 fixed the actual defect that blindness was hiding: the agentskills.io spec defines `metadata` as a map of string keys to string values, and the reference implementation `skills-ref` enforces that by coercion, not rejection - a YAML list under `metadata.chain` is silently rewritten to a string containing a Python list repr (`"['a', 'b']"`) that no consumer can parse back into names. The fix in `parseChainDeclaration` was to also accept a comma-and/or-whitespace-delimited string. That is the correct fix for the value-type defect. What ADR 0040 did not examine is what happens to a plugin that has a string-shaped `chain:` naming an invocation the contract does not permit, or whose only chaining signal is a string declaration with no contract file at all. Before this release, both of those plugins passed `S4` - not because they were conformant, but because the check could not see them. After the ADR 0040 fix, unmodified, both would fail `S4` with an `error`, moving their gate exit code and their earned tier, from a toolkit upgrade alone.

This is precisely what ADR 0027 (Standard versioning and compatibility policy) exists to prevent for a *newly added or tightened* requirement: ship `warn` for one Standard minor, then graduate to `error`. The mechanism ADR 0027 built for that is `meta.since` plus `applyStandardDowngrade`, keyed per check (per `reqId`). `S4` is not a new check - it has read the array shape and enforced orphans as `error` since the baseline (`since: "0.x"`). What is new is a *shape within* an existing check gaining reach it never had. The existing burndown machinery has no unit smaller than "the whole check," so it cannot express "the array path stays `error`, the newly-reachable string path is `warn`." That gap is why the fix has to be made explicit inside `chain-contract.mjs` itself, at the point each finding is constructed, keyed off which shape produced it - not by any change to `meta.since` or to `standard-gate.mjs`.

**How this got through.** The release plan for v1.10.1 stated the invariant plainly: no third-party plugin's tier or exit code moves in this release. ADR 0040 stated it again, specific to this exact reader change: "purely additive... no third-party plugin's `S4` verdict moves." Neither claim was verified against the orphan and missing-contract code paths before the fix shipped to review; both were asserted from the array-shape precedent, where the claim happens to be true (an array-shaped edge was already read pre-fix, so adding string parsing changes nothing for it). The gap was found by the adversarial review of PR #205, not by the author, and not by this repository's own gate - because this repository's own `agents/_chain-permitted.yaml` permits every edge it declares, so no shape of orphan is present to fail either way. A green self-hosted gate was never evidence for this invariant; it could only ever be evidence against a defect this repository happens to have.

## Decision drivers
- The v1.10.1 release invariant is explicit and absolute: no third-party plugin's tier or exit code moves. A patch release that moves a verdict is not a patch.
- ADR 0027 governs exactly this shape of problem (a tightened requirement needs a migration window) and should be honored in spirit even where its literal mechanism (`since` per check) doesn't fit a sub-check shape distinction.
- The fix must not regress the value-type defect ADR 0040 exists to close: string declarations still need to be read and their orphans still need to be discoverable, or the recommended shape (a comma-separated string) becomes unenforceable and authors have no reason to migrate off the array shape that silently corrupts under `skills-ref`.
- The gate stays deterministic and model-free (Design Principle 3): the shape/severity mapping is a pure function of what is already parsed, not a new judgment call.

## Considered options
1. **Ship as-is: every finding is `error` regardless of shape** (the code that reached PR #205, `8f31845`). Rejected: this is the defect under review. It contradicts both the release invariant and ADR 0040's own stated claim about itself.
2. **Never gate on the string shape at all - keep it non-gating permanently**, the recommendation's first form taken literally as "forever," or reverting to the pre-ADR-0040 blindness for severity purposes while still reading the shape for other purposes. Rejected: it leaves the recommended shape (a comma-separated string, which the docs actively steer authors toward to dodge the `skills-ref` coercion defect) permanently unenforceable, which is a worse place to land than a scheduled tightening. A plugin could adopt the recommended shape and never have its orphans caught.
3. **Version the tightening through ADR 0027's warn-first policy, scoped to the specific findings newly reachable by the string shape, decided at the point of construction rather than through `meta.since`.** (chosen) `warn` at Standard 0.12, `error` at Standard 0.13, mirroring the burndown ADR 0027 already established for check-level tightenings, applied here at finding-shape granularity because the check-level mechanism doesn't reach this case.
4. **Treat it like the `G4` (generated-docs drift) precedent** - ship the `error` immediately with an upgrade note in RELEASE-NOTES.md, on the reasoning that "the error is the check finally being able to see a wrong index [here, a wrong chain] rather than a new defect," exactly as v1.10.0 did for `G4`. Considered seriously; rejected for the reason in Decision outcome below.

## Decision outcome

Option 3.

**On option 4, the `G4` precedent, weighed honestly rather than dismissed.** The v1.10.0 release notes make the same argument this ADR could make for `S4`: the check isn't wrong, it's newly able to see a pre-existing problem, and treating "newly visible" as "newly broken" is itself a kind of dishonesty about what conformance meant all along. That argument is sound, and it is exactly why `G4` shipped as an immediate `error` with an upgrade note rather than a warn-first burndown. The reason this release goes the other way is not that the argument is wrong here - it is that the two releases made different promises. v1.10.0 was a MINOR release; ADR 0027's warn-first policy is scoped to tightenings, and a MINOR is where the Standard is allowed to grow. v1.10.1 is a PATCH, and this release's own stated invariant - repeated in the release plan and in ADR 0040 - is that no third-party plugin's tier or exit code moves at all, full stop, not "moves only when the check was already secretly wrong." A PATCH that moves a verdict, however defensible the underlying reasoning, is not a patch; it is a MINOR wearing a PATCH's version number. If this tightening is wanted at `error` strength, it ships as a MINOR with an upgrade note, on the `G4` precedent, on purpose, not as a side effect of a value-type bugfix riding a patch.

Per finding path, the severity table:

| Finding | Array-shaped declaration | String-shaped declaration |
|---|---|---|
| Orphan (`caller` -> `callee` not permitted by the contract) | `error`, unchanged | `warn` at 0.12; message states the 0.13 graduation |
| "Chaining used but `agents/_chain-permitted.yaml` missing," where the *only* chaining signal is this declaration | `error`, unchanged (this shape was already a pre-existing signal before ADR 0040) | `warn` at 0.12; message states the 0.13 graduation |
| "Chaining used but `agents/_chain-permitted.yaml` missing," where a contract file, `_workflows/`, or *any* array-shaped declaration is also present | `error`, unchanged | `error`, unchanged (a pre-existing signal already required the contract regardless of the string) |
| Phantom contract entry, malformed contract shape, invalid contract YAML | `error`, unchanged (not shape-dependent; these findings are about the contract file itself, not about a declaration) | `error`, unchanged |

**The no-newly-erroring invariant, reasoned through each path.** A plugin passing `S4` today has one of two states: (a) it has no string-shaped declaration at all, in which case nothing about this change touches it - every finding it could produce is on the array/contract/workflow paths, which are byte-for-byte unchanged; or (b) it has a string-shaped declaration and is passing, which under the pre-fix blindness meant either the declaration named a permitted edge (still no finding: the orphan check still only fires when `!permitted.has(target)`, shape does not change what counts as permitted) or the plugin simply had no error-severity finding elsewhere to fail on. In case (b), the newly-reachable finding is exactly the one this ADR pins to `warn`, and `runGate`'s `gateExitFromFindings` counts only `severity === "error"` findings when computing `exitCode` (`scripts/check.mjs`); `warnCount` is reported separately and feeds neither the exit code nor `ceilingIndex`/tier computation. A `warn` cannot move a tier and cannot move an exit code. There is no third path: every finding this check can produce is enumerated in the table above, and every string-shaped cell is `warn`.

## Consequences
- **Positive:** the release invariant holds as stated - no third-party plugin's tier or exit code moves in v1.10.1. The recommended string shape remains fully readable and its orphans remain discoverable, just not gate-failing yet, so authors migrating off the array shape (to dodge the `skills-ref` coercion defect) get real feedback instead of silence.
- **Negative / accepted:** `S4` now carries a shape-conditional severity that the existing `meta.since` / `applyStandardDowngrade` burndown machinery does not model, which is a small amount of check-local complexity ADR 0027's general mechanism does not cover. Documented in-line in `chain-contract.mjs` rather than generalized, because this is (so far) the only check with a sub-check-granularity tightening; if a second one appears, that is the trigger to generalize the burndown mechanism to finding-level `since`, not before.
- **Negative / accepted:** a plugin with a string-shaped orphan gets a `warn` it must still fix before Standard 0.13, or its next-release upgrade becomes the same class of surprise this ADR exists to prevent - the graduation date is a promise to a future version of this same defect class, not a resolution of it.
- **Scheduled:** the string-derived `S4` findings graduate `warn` -> `error` at Standard 0.13, alongside the rest of the scheduled vocabulary-alignment work.
- **Process lesson, recorded because the repository's habit is to write down how a defect got through:** a stated release invariant ("no verdict moves") was checked against the shape of change that was already known to be safe (array, pre-existing) and not against the shape that was actually new (string, newly parsed). A green self-hosted gate was treated as corroborating evidence for a claim the self-hosted gate structurally cannot test, because this repository's own contract has no orphan of either shape to fail on. The generalizable check for next time: when a change is claimed "purely additive, no verdict moves," construct or find a fixture that has something to lose under the new code path, not one that already passes under the old one.

## Implementation sites
- `scripts/checks/chain-contract.mjs` - the `declaredChains` mapping: each entry now carries `shape` (`"array"` | `"string"` | `"none"`), read from the same `declared` value used to compute `chain`, independent of whether it came from `metadata.chain` or the legacy top-level key.
- `scripts/checks/chain-contract.mjs` - the "chaining used but no contract" branch (`if (!hasContract)`): severity is `SEVERITY.ERROR` when `hasWorkflows || declaredChains.some(c => c.shape === "array")`, else `SEVERITY.WARN` with the `GRADUATION_NOTE` appended to the message.
- `scripts/checks/chain-contract.mjs` - the orphan-detection loop: severity is `SEVERITY.ERROR` for `shape === "array"`, `SEVERITY.WARN` (with `GRADUATION_NOTE`) for `shape === "string"`.
- `scripts/checks/chain-contract.mjs` - `GRADUATION_NOTE`, the single string constant both branches append, naming Standard 0.13 as the graduation point, so the two messages cannot drift out of sync.
- `tests/unit/chain-contract.test.mjs` - four tests added: a string-shaped orphan is `warn` and names 0.13; an array-shaped orphan is still `error` and does not name 0.13; the `chain-string-no-contract` fixture (only chaining signal is a string declaration, no contract file) produces `warn`; the same fixture mutated to an array declaration produces `error`.
- `tests/fixtures/anti/chain-string-no-contract/` - new fixture: one skill declaring `metadata.chain` as a string, no `agents/_chain-permitted.yaml`, no `_workflows/`.
- `docs/reference/askit-build-chain-contract.md` and `skills/askit-build-chain-contract/references/authoring-chain-contracts.md` - document the severity table and the Standard 0.13 graduation for anyone authoring or fixing a chain contract.

Grep anchor: `GRADUATION_NOTE` in `scripts/checks/chain-contract.mjs` (the constant both severity-conditional branches share).
