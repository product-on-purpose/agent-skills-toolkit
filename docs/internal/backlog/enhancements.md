## E1 - Designed evaluation report (HTML + Markdown), shared across the assessment skills

- **Target:** `askit-evaluate` first, then the broader assessment / advisory family (see "Which skills" below).
- **Change:** over the ONE structured report object `scripts/evaluate.mjs` already produces, add `--format=md|html` renderers (alongside terminal + `--json`), so MD / HTML / JSON never diverge. The HTML is a **self-contained** page (inline CSS; a small amount of inline JS for the TOC scroll-spy and the copy-prompt buttons is allowed; no external assets, no binaries).
- **Information architecture (designed thoughtfully):**
  1. **Masthead / verdict** - subject, report type, date, the headline grade (tier earned), a climb indicator, and key stats (checks passed, blockers, warnings, gate exit code).
  2. **Executive summary** - for a non-engineer: what was evaluated, the verdict, the top findings, the recommended next move.
  3. **What was evaluated / component breakdown** - the subject's identity (declared tier, version, agent-targets, prefix), its components and functionality, anatomy.
  4. **Methodology & scope** - the three layers (deterministic conformance decides the tier; behavioral and review sit beside it), the legend, and a confidence / limitations note (which findings are exact vs judgment; vacuous passes such as `G1`/`G6`).
  5. **Tier compliance - evidence ledger** - per tier (Bronze / Silver / Gold) a verdict bar plus a row per requirement: status, the evidence (what was found, file:line and check module), and for every non-compliance a short **why it matters** explanation with impact.
  6. **The climb / burndown** - exactly what blocks the next tier, ordered, with effort estimates.
  7. **Improvement path** - a card per gap: the issue, the fix, a **copy-paste prompt** that executes it with the toolkit's own skills, plus priority and effort.
  8. **Insights** - qualitative observations and strategic notes beyond pass / fail.
  9. **Evidence & sources** - citations grounding each finding (check module, Standard clause, file).
  10. **Report metadata** - subject and Standard versions, evaluator, gate exit, timestamp, and the status / severity legend.
- **Hard UX constraints (maintainer, 2026-06-03):** **no content hidden behind tabs or expanders** (everything visible, linear scroll); a **left-docked TOC** (sticky, with a scroll-spy active state); a print / Save-PDF affordance; on-brand (the family `#5C7CFA` plus the Bronze / Silver / Gold palette). This supersedes the earlier "collapsible per-rule sections" sketch.
- **Sample templates:** `docs/internal/template/evaluation-report--plugin.html` (and siblings) demonstrate the IA and visual language the renderer should target.
- **Which skills could / should have a report (the report is a shared pattern, not a one-off):**
  - `askit-evaluate` - the conformance + behavioral + review report (this item).
  - `askit-migrate` - a **migration assessment**: current state, gap-by-tier, and the staged Bronze-to-Gold roadmap (same IA; the "improvement path" becomes the staged plan).
  - `askit-capability-advisor` - a **readiness report**: the per-agent capability matrix and the recommended target tier before building.
  - `askit-release` - a **release-readiness** report: the gate result, the changelog / notes summary, and a go / no-go.
  - `askit-reviewer` - a **review report**: qualitative findings with severity (the judgment layer rendered).
  - the behavioral mode (`askit-quality-grader`) - a **behavioral report**: per-case fire / no-fire and output-quality verdicts.
  Recommend ONE shared report renderer (a `report-render` lib over the report object, plus the IA above) parameterized by report type, not per-skill bespoke HTML - matching the toolkit's generation-over-duplication ethos.
- **Why:** serves the "summary AND detailed" plus visuals requirement (ADR 0021 / 0024); makes results consumable by non-engineers (HTML) and agents / PR review (Markdown), not only in the terminal or as JSON; a designed, shareable, copy-paste-actionable report is part of the best-in-class differentiator.
- **How to apply (sketch):** one renderer over `evaluate.mjs`'s report object; portable Node, no new runtime, no binary assets (preserves the "CI only shells out to portable scripts" principle). The MD format reuses the summary-plus-detailed convention; the HTML matches the sample templates.
- **Tier / phase:** enhancement; v1.x. Strong candidate to pair with the docs / visuals build-out.
- **Status:** backlog (recorded 2026-05-31; expanded 2026-06-03 with the full IA, the no-tabs / left-TOC constraints, the shared-pattern skill list, and a sample template in `docs/internal/template/`).

### E14 - U5 assumes English, and is unpassable in any language it does not know  [calibrate, effort M, ADR-gated]

- **Target:** `scripts/checks/description-score.mjs` (`U5`).
- **The measurement (corpus batch 3, reading 18):** across 349 French skills, `U5`'s `WHEN` trigger pattern fired on **0 of 346** parseable descriptions, while **341 of them carried an explicit French trigger clause**. Same-batch English controls: 705 of 1016, and 134 of 136. Because `WHEN` is worth 0.35 of a 1.0 score against a 0.7 threshold, a description the pattern cannot match caps at **0.65**. No French description can pass, however good. The clearest case scored 0.30 while containing "A utiliser quand l'utilisateur veut relire, corriger ou ameliorer un texte francais", a word-for-word rendering of the exact construction the pattern rewards.
- **Scope, stated precisely so this is not over-read:** this is **one check of thirty**, and it carries `house` provenance, so `--profile plain-plugin` (the honest third-party grading mode) **drops it entirely**. A non-English library graded the way you would grade someone else's work never sees this. The defect bites only a library that adopts this Standard, declares a tier, and writes non-English descriptions. Every other check is language-neutral: a link resolves or it does not, a diagram parses or it does not, a manifest matches disk or it does not.
- **Change:** an ADR that answers a design question, not a patch that adds French patterns. Adding French vocabulary moves the same cliff one language over and leaves German, Japanese, and Portuguese exactly where French is now. The real options are (a) detect the description's language and score only where a lexicon exists, reporting "not scored" rather than a failing number elsewhere; (b) a pluggable per-language lexicon with English as one entry rather than the hardcoded default; (c) a language-independent structural signal for "states when to use it" (for example the presence of a conditional clause) with the lexical match as a bonus rather than a requirement; (d) scope `U5` explicitly to English in the Standard and say so, which is honest but caps the Standard's reach.
- **Recommendation:** (a) or (c). Option (d) is the cheap answer and should not be taken by default, because the limitation is one heuristic in one check, not a property of the Standard.
- **Related upstream constraint, not ours:** the agentskills.io spec requires `name` to be lowercase ASCII with hyphens, which independently constrains non-Latin-script naming. That is upstream's rule; `askit-standards-watch` now tracks that file.
- **RESOLVED 2026-08-15 by ADR 0049, shipped in v1.14.0.** `U5` gains a NOT-SCORED outcome: below an English function-word density of 0.10 it emits nothing, and the decline is counted separately so silence and a pass are distinguishable. Measured: the French corpus goes from 346 findings to 3, for a cost of 3 descriptions in 1376 across every English corpus combined. The floor came from a sensitivity sweep over 2068 descriptions in seven pinned corpora, not a guess.
- **THIS ENTRY'S OWN RECOMMENDATION WAS FALSIFIED, and that is the part worth keeping.** It recommended option (a) or (c). Option (c) - a language-independent structural signal for "states an occasion" - was operationalised and measured: it fires on **99.9 percent** of all 2068 descriptions, including 94.4 percent of Anthropic's own, so it cannot discriminate and cannot be a scoring component at all. Option (b), a pluggable French lexicon, reached only 33.2 percent against a corpus where 341 of 346 carry an explicit trigger clause. What shipped is option (a) in spirit but NOT via a language detector: the question is narrower than "what language is this", it is "can my lexicons read this".
- **The residual is stated rather than rounded away:** 3 of the 346 still fail, being French descriptions with enough English loanwords to cross the floor. This reduces a systematic defect to a rare one; it does not eliminate it.
- **Status:** RESOLVED 2026-08-15 (v1.14.0, ADR 0049). Recorded from corpus batch 3 reading 18; deferred from v1.8.0 (R2) per release risk R2-5.

### E15 - three F2 eval-run runner defects found by corpus batch 3  [fix, effort S each]

- **Target:** `scripts/lib/eval-run.mjs` and `scripts/lib/eval-run-aggregate.mjs`.

### E16 - advisory-score credits nothing when one finding engages two defect entries  [fix, effort M, blocks publishing any cell as final]

- **Target:** `scripts/lib/advisory-score.mjs` (`classifyFinding`, `scoreAdvisory`), and the `review-required` outcome in the seeded-defect scoring key.
- **Change:** define and implement a scoring rule for a finding whose `matchText` satisfies the `locate` clause of more than one defect entry. Today it becomes `review-required` and is credited to neither entry, which suppresses precision and recall together.
- **Why:** sensor reading 26 (2026-08-04). The E13 triple produced the proof. The same Opus advisory scored **0.42** precision against key 1.0.0 and **1.00** against key 1.1.0 with no change to the advisory at all, and seven of its twenty-three findings are still uncredited because each engages two entries at once. The effect is that the more granular a review is, the worse it scores: a model that writes exactly one finding per planted defect is rewarded, and one that describes the same reality in richer detail is penalised. `precision` therefore currently measures conformance to the key's granularity rather than correctness, and no cell can honestly be published as final until this is settled.
- **Options to weigh in the fix:** credit the first unsatisfied entry and mark the finding a partial for the rest; credit every entry it genuinely satisfies (changes the meaning of `recall`'s denominator); or require the key's `locate` clauses to be disjoint enough that this cannot arise (the integration test already enforces disjointness across *examples*, which is weaker).
- **Status:** OPEN. Raised by E13.

### E46 - the Standard defines a list-valued `metadata` key that cannot be declared without failing validator parity  [correctness, effort S, found building the capability family]

- **Target:** `scripts/check-parity.mjs` (the `metadata-parity` section), `STANDARD.md` sec 3.7.
- **Found by:** authoring `askit-capability-whats-new` and `askit-capability-gap-analysis` on 2026-08-18. They are the **first components in this library to declare a list-valued `metadata` key**, which is why this has never surfaced before.

**The contradiction, in two sentences.** `STANDARD.md` sec 3.7 defines `agent-targets` as a conventional `metadata` key and types it **(list)**. Declaring it on a skill makes `npm run check-parity` report a blocking `metadata-parity` MISMATCH, and that section has **no documented-exception path** - so a component conforming to sec 3.7 fails a gating harness.

**The reproduction, verbatim from the run:**

```
[MISMATCH] skills/askit-capability-whats-new
  metadata.agent-targets: coerced-non-string - ours=["claude-code","codex"] reference="['claude-code', 'codex']"
```

Our loader parses the block sequence into an array. The agentskills.io reference parser returns it as a **Python-repr string**. Both readings are defensible; they simply disagree, and `metadata-parity` correctly reports a disagreement it has no way to adjudicate.

**A second, separate finding from the same session, worth recording because it bites first.** The reference parser rejects YAML **flow** sequences in frontmatter outright:

```
agent-targets: [claude-code, codex]
               ^ Found ugly disallowed JSONesque flow mapping
```

Block-sequence form parses cleanly. So a list-valued key written the compact way fails `claude plugin validate --strict` **and** the reference parser, while the block form passes both and then trips `metadata-parity` instead. Neither failure is documented anywhere a plugin author would look.

- **Why this matters beyond this repository:** `agent-targets` is not exotic. It is one of seven keys sec 3.7 names, it is the natural way to declare cross-agent intent, and `askit-capability-advisor` advises authors about agent targeting. **Any plugin author following the Standard hits this.** The toolkit currently avoids it only because no skill happened to declare the key.
- **Options, none chosen:** (a) teach `metadata-parity` to compare list values structurally, so a coercion difference on a list is not a mismatch - smallest change, but it edits a gating harness to accept a real disagreement; (b) have sec 3.7 state the block-sequence requirement and document the coercion as known, closing the author-facing half without touching the harness; (c) both. **Measure first:** count how many skills across the pinned corpora declare any list-valued `metadata` key before deciding, per the standing rule that a recommendation depending on a population must count it.
- **Workaround in force today:** both new skills omit `agent-targets`, matching every other skill in this library. **That is a workaround and not a fix** - the metadata is genuinely useful for these two, and it was dropped to keep a gating harness honest rather than because it was wrong.
- **Status:** OPEN (recorded 2026-08-18).
### E45 - a pinned action's version comment is unchecked, and superseding Dependabot blinds the watcher that would have caught it  [correctness, effort S-M, network-bearing, found triaging Dependabot #224 to #228]

- **Target:** the `uses:` pins across `.github/workflows/*.yml`; a new maintainer-only script under `scripts/`, beside `vendor-watch.mjs` and `release-ready.mjs`. Explicitly **not** `scripts/checks/`, which is the closed spine registry `registry.mjs` imports by name (the same placement reasoning as `release-ready.mjs`, decision 1 of the v1.14.0 cut).
- **Found by:** triaging Dependabot PRs #224 to #228 on 2026-08-17. Neither half is visible from inside a single PR diff; both needed the repository's PR history read as a series.

**Half one: a SHA pin's comment decays into a lie on every bump, and only a human has ever caught it.**

`codeql.yml` pins all three `codeql-action` steps by SHA with a trailing comment, `# v4.37.6 pinned 2026-08-09`. Dependabot advances the SHA and leaves the comment untouched, because it rewrites a bare `# vX.Y.Z` and this repository's comments carry trailing prose that falls outside the pattern it matches. So the machine-readable half and the human-readable half disagree, and the human-readable half is the only one a reviewer reads.

| Dependabot PR | Superseded by | What the comment said afterwards |
| --- | --- | --- |
| #187 | #188 (v4.37.5 re-pin) | stale |
| #198 | #199 (v4.37.6 re-pin) | stale |
| #225 | #234 (v4.37.7 re-pin) | stale |

Three occurrences, three catches, all by eye. #199's commit message already diagnosed it in 2026-08-09 ("What Dependabot got wrong is the COMMENT") and the fourth occurrence still arrived. A defect caught three times by a human reading a diff is the repository's standing definition of something that needs a guard, not another correction.

**Half two: the remedy for half one is what blinded Dependabot to `vendor-watch.yml`.**

`vendor-watch.yml` shipped in v1.14.0 pinning `actions/checkout@v4` while the other six workflows had been on `@v7` since #179. Dependabot reported `setup-node` 4 to 7 out of that file (#226) and never reported `checkout` 4 to 7 in the same file. The history is a clean natural experiment: #150 (`setup-node` 5 to 7) was **merged**, #159 (`checkout` 5 to 7) was **closed** in favour of the hand-written #179. Same ecosystem, same version shape, same cross-file conflict shape; the only difference is merged versus closed, and closing a Dependabot PR stops it proposing that dependency version.

So the supersede-by-hand habit that fixes half one buys a correct comment at the price of blinding the watcher to that dependency's next occurrence. #225 was closed on 2026-08-17 for exactly that reason, which means `codeql-action` has now inherited the same blind spot, and `codeql.yml`'s pins are watched by nothing.

**Why one check closes both halves.** A script that resolves every `uses:` pin against the registry it came from can report two facts from one lookup: whether the trailing comment names the version the SHA actually resolves to (half one), and whether the pin is behind the action's current release (half two, and it does not care whether Dependabot is willing to say so). The two halves are the same question asked of the label and of the pin.

- **Design sketch:** parse `uses: <owner>/<repo>@<ref>` out of every workflow; for a 40-hex ref, dereference the annotated tag and match the resolved version against the trailing comment; for a `vN` ref, compare against the latest release. Exit codes should follow `vendor-watch`'s discipline exactly: 1 when a label disagrees or a pin is behind, **2 when a lookup could not be performed**, because an unreachable registry proves nothing and a refusal is never a pass. Same reason `vendor-watch` is write-incapable by construction, this must be too: it reports, a human re-pins.
- **Why it is not fixed in place, and was not smuggled into the dependency triage:** it needs network access from a check context, an entry in the `scripts/` folder README or G8 fails, and a decision about whether it joins `release-ready`'s exit code or stays advisory. That is release scope with an ADR-sized question in it, not a rider on a version bump.
- **Cheap partial available today, if the full check is deferred:** add `vendor-watch`-style coverage for nothing at all, and instead simply stop closing Dependabot PRs. Merging #225 and following it with a comment-only correction commit would have kept `codeql-action` visible to Dependabot at the cost of one extra commit. Recorded because it is the zero-code mitigation and nobody had noticed the trade existed.
- **SCHEDULED 2026-08-18 as W2 of v1.15.0**, packet at [`release-plans/plan_v1.15.0/RELEASE-PLAN.md`](../release-plans/plan_v1.15.0/RELEASE-PLAN.md). ADR-first, per the v1.14.0 pattern. **A baseline probe of the sketch above was run before scheduling it, and it exits 1 today:** 29 `uses:` pins across 7 files, 8 distinct actions, **0** lookup refusals, **0** pins behind their action's current major, and **1 label disagreement** - `release.yml:91` pins `softprops/action-gh-release@3d0d9888` with the comment `# v3 pinned 2026-07-26`, and that SHA resolves to tag **`v3.0.2`**.
- **That one instance sharpens the ADR's central question, and it is not the codeql case.** `# v3` is **not false**; `v3.0.2` is a `v3`. It is **under-specified**, which is a different defect with the same consequence: when `v3.1.0` ships and someone advances the SHA, `# v3` stays literally true while naming nothing a reviewer can check. So the rule the check enforces has to be chosen deliberately - *"the label must not be false"* passes this line, *"the label must name the version the ref resolves to"* fails it - and there is now a live instance to decide it against rather than a hypothetical. The packet recommends the stricter rule, because the weaker one passes exactly the under-specification that hides the next bump.
- **Status:** **IMPLEMENTED in v1.15.0** as `scripts/action-pin-watch.mjs` with [ADR 0053](../decisions/0053-a-pin-label-is-a-claim-and-behind-is-not-a-defect.md) (recorded 2026-08-17, scheduled and shipped 2026-08-18). **Half one is closed by a machine**: every SHA pin's label is now resolved against the registry and a disagreement is a non-overridable release blocker. **Half two is NOT closed and cannot be by this check** - it reports a pin that is behind without blocking, and it cannot make Dependabot resume proposing a dependency it was told to stop proposing. ADR 0053 therefore adopts the zero-code mitigation as standing guidance: **prefer merging a Dependabot PR and correcting the comment in a follow-up commit over closing it.** Half one had been corrected by hand for the third time in #234; half two in #235.

### E41 - adversarial-review prompts were silently corrupted by shell command substitution  [practice, effort XS to fix, affects every recorded review]

- **Target:** this repository's release practice, and any future invocation of `codex-companion.mjs adversarial-review` from the Bash tool.
- **The defect:** the review command is invoked as `node codex-companion.mjs adversarial-review "<prompt>"` with the prompt in **double quotes**, and a prompt that names identifiers in backticks - the house style everywhere else in this repository - hands bash a command substitution. Every backtick-delimited term is **executed as a command and replaced by its output**, which for `library.json` or `askit.config.json` is an error to stderr and an empty string in the prompt.
- **Measured 2026-08-13 across the v1.13.0 pre-implementation review:** **8 of the last 12 rounds** ran with corrupted prompts, at 1 to 8 substitutions each. The evidence is in each run's own log as `command not found` lines before the Codex thread starts. Round 18's first attempt lost `askit.config.json`, `standard`, `message` and two others.
- **Why it matters more than it looks:** the corruption deletes exactly the terms a focused review prompt exists to name. The surrounding prose survives, so the reviewer still returns plausible findings and the run looks successful - which is why seventeen rounds passed without anyone noticing. **No prior round can be assumed to have covered any particular symbol**, and a review that was told to examine a named function may never have seen the name.
- **The fix, which is one character class:** single-quote the prompt argument, or strip backticks from review prompts entirely. Single quotes make backticks literal in bash.
- **The general lesson, which is this repository's own recurring one:** a harness that fails silently and returns a plausible result is the failure mode this project has now hit three times - the `NODE_AUTH_TOKEN` fallback that would have published without provenance, the killed review run that left a stale `verdict: approve` in its buffer, and this. ### E39 - a check that SKIPPED and a check that PASSED are indistinguishable  [build, effort L, protocol change]

- **Target:** `scripts/lib/registry.mjs` (`runAllChecks`), every module in `scripts/checks/`, `scripts/evaluate.mjs` (plugin and component scopes), `scripts/lib/marketplace/evaluate-marketplace.mjs`, the `--json` contract, and `scripts/lib/report-render.mjs`.

### E38 - a subject's own config can lower an objective finding and still publish green  [design, effort M, ADR-gated]

- **Target:** `scripts/lib/resolve-config.mjs` (`resolveFindings`, the published-verdict clamp at line 55), `scripts/lib/profiles.mjs`.
- **The hole:** in `published-verdict` mode the trust clamp lifts an objective or vendor-cited finding back to `warn` only when it was turned **off** or **suppressed**. A per-rule override to `"warn"` is not clamped at all, so `rules: { "U6": "warn" }` in the subject's own `askit.config.json` produces a published verdict with no gate-failing error, from config alone, with no change to the plugin. This is general and pre-existing: it applies to every objective check today and needs no graduation to reach.
- **The FIRST rejected design, kept because the counterexample that killed it is easy to re-derive.** The v1.13.0 pre-implementation review (round 1) found the hole and recommended a blanket floor: config cannot lower an objective or vendor-cited finding below its post-pin declared severity. **Round 2 killed it.** `profiles.mjs:43` sets `U4: "warn"` under `plain-plugin`, and `U4` (name-matches-dir) is `vendor-cited`. That is a deliberate ADR 0031 calibration: real third-party plugins use a skill name as a display label or namespaced command, so name-vs-dir divergence should inform a vanilla plugin rather than fail it. The naive floor restores `U4` to `error` and fails plugins that pass today, in the exact mode this project relies on for honest third-party grading. Exempting profiles from the floor instead hands the bypass straight back, since a subject can select `plain-plugin` themselves.
- **The second rejected design, and why deferring was also rejected.** After the blanket floor was killed, the plan deferred this entry to a later cut on the grounds that the hole is general and pre-existing. Round 4 closed that off: **before v1.13.0, `rules.U13 = "warn"` is a no-op**, because `U13` already emits `warn`. Graduating it and adding `U14` therefore creates two bypassable gate-failing requirements that do not exist today, so deferring would have shipped them rather than merely leaving an old hole open.
- **PLANNED RESOLUTION in v1.13.0 (W1, ADR 0044) - DESIGNED, NOT YET IMPLEMENTED.** Round 16 caught this entry saying "RESOLVED" while its own status line said "scheduled", ADR 0044 is unratified, no code exists, and the live resolver still permits subject-owned reductions. Recording a trust-boundary defect as closed before the fix ships is how it drops out of release verification, so the state is stated once and honestly: **the design below is agreed; the bypass is still open.** It becomes resolved when ADR 0044 is ratified, the implementation lands, and the published-verdict matrix rows pass. The design introduces **CONFIG PROVENANCE**, a distinction the codebase did not draw. Every resolved setting is either **grader-owned** (a CLI flag) or **subject-owned** (read from the subject's `askit.config.json`, including its `profile` key). In `published-verdict` mode, no subject-owned setting may lower an objective or vendor-cited finding. `plain-plugin`'s `U4: "warn"` survives a grader's `--profile plain-plugin`, so ADR 0031's calibration is untouched; a subject writing `profile: "plain-plugin"` into its own config gets no reduction, so the exemption cannot be self-granted.
- **The algorithm, in the form that survived eight review rounds** - three earlier phrasings were each wrong in a different way, so it is written out rather than summarised:
  - The trust step computes the **trusted resolution**: the module's declared severity, then grader-owned profile, then grader-owned rule, in normal precedence, with every subject-owned setting absent. It does **not** "restore the declared severity" - that phrasing discarded a grader's own deliberate `--profile plain-plugin` reduction of `U4` and reset it to `error`.
  - **A rank guard makes it raise-only:** `effectiveSeverity = max(subjectResolved, trustedResolution)` by rank. Without it, a subject writing `rules.U7 = "error"` on a module that declares `warn` - being *stricter about itself* - would be dropped back to `warn`, turning a deliberately failing published verdict green via the mechanism built to prevent exactly that.
  - **Suppression is decided independently of severity.** A subject-owned suppression is cleared; a grader-owned one is left alone. `gatingFindings` requires `error` AND `!suppressed`, so a severity-only fix is fully bypassable by a waiver.
  - Ordering is trust step first, ceiling last, and the trust step can never lift a finding above its ceiling.
- **A GUARANTEE THAT WAS HERE AND IS FALSE, corrected 2026-08-13 by round 13.** This entry previously said closing E38 "cannot move a verdict red-ward for anyone pinned below the graduation version". **That holds only for a finding a BINDING Standard ceiling lowers again**, and plenty of findings have none. `U4` (name-matches-dir) is an uncapped baseline check with `since: "0.x"` and no `migration`: at pin **0.12**, a subject-owned `plain-plugin` profile lowers it to `warn` today, the trust step restores `error`, and **no ceiling exists to lower it back**. That is a green-to-red move at an old pin. The v1.13.0 plan says as much in its own "five things that look like failures" section - published-verdict mode can now fail where it passed - so the absolute guarantee written here contradicted the release it was describing, and would have excused exactly the impact measurement it most needs.
- **The correct statement:** red-ward movement in `published-verdict` mode is possible **at any pin** for any objective or vendor-cited finding without a binding ceiling, and it is confined to that mode. Compatibility measurement must include an **older-pinned, uncapped, published-verdict** case - `U4` at pin 0.12 under a subject-owned `plain-plugin` is the concrete one - rather than only the capped `U13` cases, which are the ones that happen to look safe.
- **A claim that WAS in this entry and is false, kept as a correction:** that provenance also fixes a reachable grader-owned over-fire. It does not, because none exists. `plain-plugin` turns off only `HOUSE_REQIDS`, which the clamp skips by provenance, and its one non-house entry lowers `U4` merely to `warn`, which the clamp never touches. The CLI accepts only `--mode` and `--profile`, so no grader-owned rule or suppression input exists at all. The grader-owned branch is a **forward guarantee** for a flag nobody has built yet, not a current defect.
- **Notice compatibility, also corrected:** an earlier version said the floor's notice would "compose" with `clampNotice`. It cannot - either order produces a self-contradicting report. There is one `trustNotice`, and `clampNotice` is mirrored for one minor **only where the old clamp would have fired and the final severity is `warn`**, because stamping "clamped to warn" on a finding that now ends at `error` would make the deprecated field lie to the automation still reading it.
- **The mode's documented guarantee is reversed deliberately and in writing.** `resolve-config.mjs:23-24` states the clamp "only ever raises off->warn, never to error, so turning the mode on can never flip a passing gate to failing". ADR 0044 reverses that for subject-owned reductions in this mode, and the stale sentence is corrected in the same change - a guarantee that protects the subject is the wrong guarantee in the one mode built to publish a verdict about the subject.
- **RESOLVED 2026-08-13 in v1.13.0 W1c, by ADR 0044's trust step.** In `published-verdict` mode, for `objective` and `vendor-cited` findings only, the resolver recomputes the TRUSTED RESOLUTION - the same precedence with every subject-owned setting absent - and takes it only when the subject's own result ranks lower. Severity and suppression are decided independently, because a gate needs `error` AND `!suppressed` and a step that raised only severity would leave a subject-owned waiver intact.
- **BOTH rejected designs, recorded because each was killed by a different counterexample and both are easy to re-derive:**
  1. **A blanket floor - "config cannot lower an objective or vendor-cited finding".** Killed by `plain-plugin`: `profiles.mjs` deliberately sets `U4: "warn"` per ADR 0031, so the blanket rule restores `U4` to `error` and fails plugins that pass today, in the exact mode this project relies on for honest third-party grading.
  2. **Exempting profiles from the floor.** Hands the bypass straight back: a subject writes `profile: "plain-plugin"` into its own `askit.config.json` and the exemption is self-granted. Matrix rows 2 and 3 are the same profile with different owners and opposite answers.
- **The deferral was also rejected, and that is the third thing worth keeping.** Before this release `rules.U13 = "warn"` is a NO-OP, because `U13` already emitted `warn`. Graduating `U13` and adding `U14` creates two bypassable gate-failing requirements that do not exist today, so deferring would have SHIPPED them rather than postponed them.
- **What made it solvable was a concept the codebase did not have: CONFIG PROVENANCE.** The distinction that survives both counterexamples is not what the setting is but WHO CHOSE IT. A grader selecting `--profile plain-plugin` is choosing a rubric to publish against; a subject writing the same string into its own file is grading itself.
- **Status:** RESOLVED 2026-08-13 (v1.13.0 W1c, ADR 0044). Recorded 2026-08-12 from rounds 1, 2 and 4 of the v1.13.0 pre-implementation adversarial review.

The same test passed `validate-windows` on all three of that day's CI runs, so it is environment-dependent, not a behavioral regression.
- **CORRECTION, 2026-08-12, round 3 of the v1.13.0 pre-implementation review: this entry prescribed ONE fix for TWO cases that do not share a mechanism, and the prescription is right for one and wrong for the other.** Read the two tests before acting on the bullets below.
  - **Case A, "a taskkill helper that starts and stays alive"** (`resolve-bash.test.mjs:373`). This one uses `_testStuckHelper`, described in its own comment as "genuinely long-running (but self-terminating, so it does not litter the machine)". Here the bar IS the helper's lifetime and the original prescription holds exactly: **do not widen the bar, widen the gap.** Raising the bar above the helper's lifetime destroys the only thing separating "the process did not wait" from "the process waited and the helper happened to die".
  - **Case B, "write-then-hang"** (`resolve-bash.test.mjs:213`). This one has **no helper lifetime to widen.** Its candidate is `while true; do sleep 1; done` - it hangs **indefinitely** - and the assertion at line 237 is `elapsedMs < 700 + 2000 + 3000`, a wall-clock budget of `timeoutMs` plus the module's `KILL_GRACE_MS` plus a 3000 ms margin. Because the candidate never exits on its own, **any finite bound proves the supervisor enforced its own timeout**, so widening the margin here preserves the test's discriminating power completely rather than deleting it. The failure is that a loaded workstation exceeds the 3000 ms margin, and the margin is the only part that is arbitrary.
  - **The two fixes are therefore different, and applying the entry's original blanket rule would have fixed Case A, left Case B failing, and left `npm run release-counts` non-zero.** That is exactly the release-gate blocker recorded above.
- **Do NOT "fix" Case A by widening the threshold**, per the reasoning above; **the right fix for Case A is to widen the GAP**, giving the stuck helper a much longer lifetime (30 s or more) so that an exit at 5 s is unambiguous under any plausible scheduling delay, and keeping the assertion against the helper's lifetime rather than a fixed number.
- **Why it is filed rather than fixed here:** it sits in the same helper the previous release hardened over four review rounds and deliberately stopped hardening (see E32). A timing change there deserves its own measured pass, not a rider on a patch release resolving unrelated review findings.
- **ESCALATION, measured 2026-08-12 during the v1.13.0 planning pass: this is not only a flaky test, it blocks the release-time counts gate on the maintainer's workstation.** `scripts/check-release-counts.mjs` compares BOTH halves of a stated count - `c.total !== authoritative.total || c.failures !== authoritative.failures` at line 210 - so while E37 fails locally, `npm run release-counts` reports drift against any truthful "N tests, 0 failures" claim and exits non-zero. `docs/internal/RELEASE.md` and every release plan since v1.11.0 name that command as non-negotiable, so a release cannot complete its own stated verification protocol on this machine until E37 is fixed or the run is performed somewhere clean. Measured at `8b55840`: full suite 1013 tests / 1 failure locally, the same two cases 2-of-9 failing in isolation (load-dependent, E37's signature), and `validate-windows` green on CI for the same commit. This raises the entry from `[test-quality, effort S]` to a release-mechanics blocker; the fix itself is unchanged and still small.
- **RESOLVED 2026-08-13 in W6 of the v1.13.0 cut.** `KILL_GRACE_MS` and a new `STUCK_HELPER_LIFETIME_MS` are exported from `tests/unit/_resolve-bash.mjs` as timing contracts; Case B's bound is now `timeoutMs + KILL_GRACE_MS + SCHEDULING_SLACK_MS` with no literal `2000` anywhere in the test; Case A's outer guard derives from the helper's lifetime, which moved from 5000 ms to 60000 ms; and every case that orphans a process now cleans up after itself from a `finally`, addressing processes by a marker scoped to the owning pid. Verified: both cases 5 of 5 under spawn-heavy load, `npm run release-counts` exit 0 against 1013 tests / 0 failures, gate Advanced 0/0, and a full suite run leaving **zero** leftover processes where it previously left about five.
- **Three things measurement corrected in the prescription above. Read these before trusting any similar plan.**
  1. **The process that accumulates is the CANDIDATE, not the helper.** This entry and the release plan both said to reap the helper. The helper cannot outlive its parent on Windows at all - traced directly: alive at the instant the inner process closed, gone by the next poll, while the candidate survived indefinitely. The orphan is the probe candidate, `while true; do sleep 1; done`, which never exits and whose tree-kill these cases deliberately disable. The helper assertion is still there and now discharges as a guarantee rather than an expectation.
  2. **"30 s or more" was not enough on its own.** At a 30000 ms lifetime with a bar derived as a third of it, Case A still failed **1 run in 5** under load. Any bar is a claim about how fast the machine is; what fixed it was a longer gap (60000 ms) with the guard at half of it, sized against measured worst cases rather than against comfort.
  3. **Asserting that the cleanup must succeed re-created the flakiness.** A first version failed the case when a candidate survived its forced kill - which happens: one orphan survived under load and then died on the first attempt once the machine was idle. That is E32, deliberately unfixed, so failing on it puts a deferred defect back in the way of every loaded run. The cleanup now retries three times with a lengthening window, fails only on a surviving HELPER (this file's own scaffolding), and reports a surviving CANDIDATE as E32 residue via `t.diagnostic`.
- **A note on reproducing it:** CPU saturation does not. 48 busy processes on 32 cores left all nine cases passing. These timings are dominated by process spawn, so the pressure that moves them is process-tree and memory contention - the shape of the original failure, a workstation carrying 32 leaked toolchain processes with 189 node children.

### E32 - a rejected probe candidate can survive a kill Node reports as successful  [hygiene, effort M, deliberately deferred]

- **Target:** `tests/unit/_resolve-bash.mjs` (`killProcessTree`, `runUnderSupervisor`).
- **The observation, measured during the v1.11.1 cut:** when the shell probe rejects a candidate on timeout, the calling process reliably stops waiting and exits within a bounded time. The candidate's own OS process is a different matter. An orphaned `bash.exe` can survive even when `child.kill()` returns `true` and Node's `exit` and `close` events fire promptly with `signal: SIGKILL`, so **Node genuinely believes the kill succeeded**. Instrumented with timestamped logging and reproduced independent of system load. It traces to how Git-Bash/MSYS represents its process tree on Windows, where a Windows PID does not always correspond one-to-one with what the MSYS runtime is still doing underneath it, rather than to a flaw in the kill sequencing.
- **Why it is filed rather than fixed:** the harm the pre-release review actually named was a **hang**, since `npm test` gates `npm publish` and a surviving child holding Node's event loop open converts a publish failure into a publish hang. That is fixed and verified adversarially, including `taskkill` forced to fail against a genuinely never-ending candidate. What remains is an occasional orphaned background process: **hygiene, not a block.** Closing it needs OS-level containment (a Windows Job Object configured to terminate all members on close, or equivalent), which is the correct mechanism for a production process supervisor and over-engineering inside a test helper whose only job is rejecting an unsuitable shell. That judgment was made explicitly, three review rounds into a one-line patch, and is recorded here so the next person meets a decision rather than an oversight.
- **What would change the call:** evidence that orphans accumulate across a normal development session rather than appearing occasionally under deliberately adversarial probing, or any report of one interfering with a subsequent run. Both are cheap to watch for and neither has been observed.
- **UPDATE 2026-08-12: the first half of that condition is now MET, measured, and the second half is disproved.** During the v1.12.0 cut this workstation was found carrying **68 orphaned `bash` processes**, in clusters of three whose start times map onto individual test runs, dating back eight days. They accumulate under entirely ordinary use - repeated `npm test` runs - not under adversarial probing. Rate measured directly: **63 to 85 processes across four consecutive runs of `resolve-bash.test.mjs`, about five leaked per run.** So "orphans accumulate across a normal development session" is now established fact rather than a hypothetical.
- **The interference half did NOT hold up, and that is worth recording precisely so nobody re-derives it.** The suspicion was that accumulated orphans were causing a neighbouring timing test to fail. Killing this session's orphans and re-running produced **0 of 4 passing**, exactly as before, so the failure has another cause (a wall-clock budget with no margin - see **E37**). Accumulation is real; this particular interference is not.
- **Net effect on the disposition:** the escalation condition this entry set for itself is half satisfied. Accumulation alone is still hygiene rather than a blocker - nothing has been shown to break because of it - but "neither has been observed" is no longer true and should not be repeated. The remaining question for whoever picks this up is whether ~5 leaked processes per suite run matters on a long-lived machine or a shared runner.
- **Do not fix by weakening the claim instead.** The guarantee quoted in `CHANGELOG.md` and `plan_v1.11.1/README.md` already states this limit plainly. If someone implements containment later, that quoted sentence must be corrected in the same change; a stale guarantee that undersells the code is the same defect class as one that oversells it.
- **UPDATE 2026-08-13, and read this before re-measuring: the accumulated orphans were cleared, and the workstation was NOT rebooted** (uptime unbroken since 8/3). A later session that counts zero and concludes nothing accumulates would be drawing the wrong conclusion from a cleaned machine.
- **v1.13.0's W6 removed this file's contribution to the accumulation without touching the supervisor.** The leak was not evenly spread: measured per case, the two that deliberately disable the real tree-kill (`_testStuckHelper` and `_testForceKillFailure`) leaked exactly one candidate per invocation each, and every case that let `taskkill` actually run leaked none. Those two now reap what they orphan, so a full suite run leaves **zero** where it left about five. **The defect itself is untouched and still deferred** - what changed is that the tests which sabotage the kill on purpose now clean up after their own sabotage.
- **New evidence for the escalation question, measured during that work: the forced kill is itself load-dependent.** A `taskkill /PID <pid> /T /F` against an identified orphan **failed** on a workstation under spawn-heavy load, and the same orphan died on the **first** attempt once the machine was idle. Retrying three times with a lengthening settle window absorbed it across 25 subsequent runs. So "the kill does not land" is not only about MSYS process-tree representation; it also degrades under contention, which makes a single-attempt kill anywhere in this repository a weaker guarantee than it reads as.
- **Status:** backlog (recorded 2026-08-11, during the v1.11.1 cut; orphans cleared and this file's leak closed 2026-08-13, defect itself still deferred).

### E31 - the pre-release review found the same structural error at three altitudes; the pattern deserves a check  [design, effort M]

- **Target:** `.github/workflows/`, and whatever mechanism ends up encoding the rule.
- **The observation, from v1.11.0's four review rounds:** three separate findings, two of them critical, were **the same error one altitude apart**. Each fix was correct at the level it addressed and left the level above untouched.
  1. `deploy-pages.yml` pinned `ref: main` inside the workflow, which cannot bind a dispatch that executes an **older copy** of that same workflow.
  2. `publish-npm.yml` proved tag ancestry using verifier scripts checked out **from the candidate commit**, so a candidate shipping stubbed verifiers proved itself.
  3. `publish-npm.yml` then moved the trust root into the workflow, which cannot bind a dispatch that executes a **hostile branch copy** of that workflow.
- **The rule that resolves all three:** *a control that lives inside the artifact it controls is not a control.*
- **Correction, round 5 of the same review, and it is the most instructive part of this entry.** The first draft of these bullets said "the only trust roots that hold are repository settings: branch protection, and environment deployment branch policies", and named `github-pages` and `npm-publish` as the surviving controls. **That is the exact overclaim commit `77b077b` had just deleted from both workflows**, left standing here. Environment protections and secrets apply only to a job that **references that environment by name**, so a hostile workflow copy renames or removes the reference and the policy never engages. Writing the correct model into the code and leaving the superseded model in the backlog would have seeded a check that certifies the vulnerable arrangement. This is the sixth instance of fix-one-place-leave-the-sibling across two releases, and it occurred inside the entry filed to record that pattern as a defect.
- **The controls, distinguished properly, since conflating them is what went wrong:**
  - **Branch protection on `main`** secures the main-side verifier in `publish-npm.yml`. This one genuinely cannot be edited by a branch copy, because the copy is not `main`.
  - **Environment deployment branch policies** gate only jobs that keep the protected environment name. They are real but narrow.
  - **npm credential binding** is what actually defeats a renamed or removed environment: an environment secret is unreadable from a job bound elsewhere, and a trusted publisher rejects a different OIDC subject. For publishing, this is the trust boundary, not the branch policy.
  - **Pages has no equivalent binding.** A renamed environment still holds `pages: write`. It is currently bounded by the accepted sole-actor risk (one collaborator, `default_workflow_permissions: read`), and the control to reach for if that changes is an Actions actor policy.
- **Why it is worth a check rather than a note:** the rule was learned three times in one release by an author who had written it down after the first time, and then mis-stated a fourth time in the note itself. Prose did not prevent instances two, three, or four. Same evidence pattern that justified `scripts/check-release-counts.mjs` in v1.10.1, where a hand-maintained number went stale four times while everyone involved was actively looking for it.
- **Candidate change, rescoped:** the naive form is now known to be wrong, so do **not** build "asserts an `environment:` is declared". That would pass a renamed environment and certify nothing. What is actually checkable in-tree is narrower and still useful: that a job granting `id-token: write` or holding a publish or deploy step names an environment **from a small allowlist recorded beside the check**, so a rename is a diff rather than a silent bypass. The settings half (does that environment carry a branch policy; is the credential environment-scoped; is the trusted publisher bound to that exact name) is **not in the tree** and cannot be asserted from it. Decide whether the release gate queries the API or whether a dated manual verification is the honest answer.
- **Watch out for:** any check here that reports success without confirming the **value** behind a setting. An environment with no branch policy satisfies a presence test while providing none of the protection. Given this entry has already produced one such wrong model, treat a green result from the eventual check as evidence only of what it literally asserts.
- **Status:** backlog (recorded 2026-08-11, during the v1.11.0 cut).

### E25 - `emitPin` inherited provenance it did not verify  [correctness, effort XS]

**Status: FIXED in v1.10.1 for both fields, with one residual noted at the end.**

The defect had two instances, and the second was found only by adversarial review after the first was
fixed, which is the part worth remembering: the same wrong rule was applied to two adjacent fields and
patching one did not prompt a look at the other.

- **Target:** `scripts/lib/standards-watch.mjs` (`emitPin`), `scripts/standards-watch.mjs` (the `--emit-pin` CLI path).
- **The defect:** `emitPin(pin, observed, { date, by = "unrecorded", repoHeadSha = null })` spreads `repoHeadSha` into the emitted `verified` block **only when it is supplied**, and the CLI never supplies it. The previous pin's value therefore survives into a document whose blob SHAs have all been refreshed around it. The `verified` block ends up asserting a verification at a commit nobody checked.
- **The reproduction (2026-08-11, during the v1.10.1 re-pin):** `npm run standards-watch -- --emit-pin` proposed `verified.repoHeadSha` of `38a2ff82958afee88dadf4831509e6f7e9d8ef4e`, the value pinned on 2026-07-27, while `gh api repos/agentskills/agentskills/commits/main --jq .sha` returned `69ef37e9424c0a7ea9dd2293b559e43ec8176379`. The emitted `verified.by` was the literal string `"unrecorded"` beside it, which is the honest default doing its job while the field next to it quietly lied.
- **Why it matters more than its size suggests:** `upstream-pin.json` exists so that a reviewer can verify every pinned value **by hand, offline, without trusting this tool**. A stale fact inside the `verified` block undermines exactly the property the file is for. It was caught by the documented human-review step, which is the process working; the repository's standing position is that a correct outcome depending on someone remembering to look is not yet a fix.
- **The second instance, found by adversarial review after the first was fixed:** `lastUpstreamCommit` behaved identically, and worse. `emitPin` clones each artifact and refreshes `blobSha` and `surface` while leaving `lastUpstreamCommit` untouched, so a re-pinned artifact names the commit that produced the **previous** bytes. The committed pin demonstrated it: `docs/specification.mdx` carried blob `d9a2db099d90` beside `lastUpstreamCommit` `6868401b` dated 2026-05-16, while ADR 0040 (re-pin after an editorial metadata clarification), written in the same change, states the observed change arrived in `217be548` on 2026-08-04. An offline reviewer following the pin would have been sent to the wrong commit and the wrong diff, which defeats the file's entire reason for existing.
- **The change, shipped:** both fields now follow one rule. `emitPin` **drops** a fact this run did not establish rather than inheriting it: `repoHeadSha` is omitted unless supplied, and `lastUpstreamCommit` is dropped whenever an artifact's `blobSha` moves unless the caller supplies replacement provenance via the new `artifactCommits` option. An artifact whose bytes did **not** move keeps its provenance, because that fact is still true. Three regression tests cover it, including the converse case, so a future refactor cannot quietly restore inheritance.

### E47 - `askit-onboard`: the adoption funnel as an interactive skill  [discoverability, effort M-L, green-lit 2026-08-20, sequenced after v1.17.0]

- **Target:** a NEW skill, `askit-onboard`. Phase 2 of the adoption system.
- **Change:** three modes following the established multi-mode pattern (`askit-migrate`'s assess / plan / adopt). **`assess`** surveys where the adopter stands - which install lane, whether a plugin exists, what components it has, which capability-map regions they have touched; read-only, reusing the `askit-explorer` subagent rather than adding one. **`plan`** interviews briefly (the `askit-init-plugin` interview mode is the voice model), picks the doors matching their goals, and writes a personalised roadmap file. **`next`** is the re-entry point, and it is the mode that makes this a process rather than a one-off.

**Why-gate statement.** The docs-layer funnel serves readers, but this toolkit's actual users are inside an agent session, and that is the highest-leverage moment to onboard them: the agent can look at their repo, tell them where they are, run the first win WITH them, and leave a roadmap that survives the session.

**The delineation, which is what makes it pass the why-gate rather than duplicate three existing skills:**

| Skill | The question it answers |
| --- | --- |
| `askit-init-plugin` | "help me start this repo" - onboards a maintainer into a NEW plugin |
| `askit-migrate` | "help me fix this repo" - onboards a REPO into conformance |
| `askit-capability-advisor` | "what can my agent run?" - advises on targets and tier BEFORE a plugin exists |
| **`askit-onboard`** | **"help me use all of this well, from where I am, over weeks"** - onboards a PERSON |

**The scope fence, and it is the entry's most important line:** `askit-onboard` interviews, diagnoses, sequences and tracks. **It routes INTO the three skills above and never duplicates their work.** The moment it starts scaffolding or fixing, it has failed its own why-gate.

- **Why now, and why NOT now.** Green-lit by the maintainer on 2026-08-20 so it stops being an unrecorded intention. **Deliberately sequenced after v1.17.0 ships and is dogfooded**, because Phase 2 automates a curriculum: validating that curriculum as cheap, editable docs first means the expensive product surface is built on a proven design rather than a guess. **Paper before automation.**
- **Depends on:** `docs/adoption/` existing and having been walked end to end (v1.17.0 W6, the dogfood walkthrough). A skill that sequences nine runbooks cannot be written before the runbooks are known to work.
- **Cost beyond the skill itself, so it is not underestimated:** a new catalogue entry, samples, and eval coverage, per the standing pattern for any new component.
- **Source material:** the full proposal is `_local/onboarding/02-proposal-askit-onboard-skill.md`, written in why-gate shape so it can be promoted verbatim. **It is gitignored and is not a followable link from this file.**
- **Status:** backlog, green-lit, unversioned. **Deliberately carries no version**, per the v1.15.0 lesson that assigning a line a version it will not get is how it goes stale unnoticed.
